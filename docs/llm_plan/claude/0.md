# Review of the Hatchet Rust SDK Design Document

## Executive summary of my validation

The document is **largely correct in its high-level recommendations** and most specific claims. My research validates:

1. **The transport and dependency choices are exactly right** — an existing unofficial Rust SDK at `eswolinsky3241/hatchet-sdk` (v0.2.8, on crates.io as `hatchet-sdk`) independently made identical choices: `tonic` for gRPC, `reqwest` for REST, `tokio`, `serde`/`serde_json`, `thiserror`, `derive_builder`, `async_trait`. This is strong external evidence for the document's transport layer design.
2. **TypeScript's `Context` vs `DurableContext` split is exactly as claimed** — confirmed in DeepWiki index of `sdks/typescript/src/v1/client/worker/context.ts` (lines 45-675 for Context, 339-576 for DurableContext).
3. **The feature-client inventory is accurate** — all three SDKs have the client accessor pattern (`client.runs()`, `client.workflows()`, etc.) that the document describes.
4. **Durable primitives are exactly as documented** — `sleepFor`, `waitFor`, `waitForEvent`, `spawnChild/spawnChildren`, `invocationCount`, replay-safe semantics are all real and documented.
5. **The Go SDK is the best systems reference** — confirmed. Its public surface (`WithRunMetadata`, `WithRunPriority`, `WithRunSticky`, `WithRunKey`, `ParentCondition`, `SleepCondition`, `UserEventCondition`, `AndCondition`, `OrCondition`) maps cleanly to idiomatic Rust.

## Important corrections and additions the document missed

These are things I found that **should be incorporated into the plan**:

1. **There is already an unofficial Rust SDK.** `eswolinsky3241/hatchet-sdk` v0.2.8 exists, uses the exact transport stack the document recommends, and is Apache-2.0. It's incomplete (only 22% documented, its `Context` only has `parent_output`, `filter_payload`, `log`, `put_stream` — no `DurableContext`, no child spawning, no retry count, no run IDs, no timeout refresh, no slot release), but it's a valuable prior-art reference that could be studied, forked, or cross-referenced rather than starting from scratch. The document's claim that parity requires a ground-up effort is correct, but not acknowledging this crate is a gap.

2. **The dispatcher uses `ListenV2`, not `Listen`.** The current (non-deprecated) worker-to-engine streaming RPC is `ListenV2`, with heartbeats on a separate `Heartbeat` RPC fired every 4 seconds. The legacy `Listen` embeds heartbeats into the stream. Rust should target `ListenV2` with `Listen` fallback, which is what the TypeScript SDK does.

3. **Exact protocol and numerical constants matter.** The scheduler payload threshold is **3 MB** for gRPC. Bulk operations are batched at **500 workflows per batch** in both TS and Python. The action ID format is lowercase `{namespace}{workflow-name}:{task-name}`. Sleep durations use Go duration strings (`"ns"`, `"us"`, `"ms"`, `"s"`, `"m"`, `"h"`). These must be replicated exactly.

4. **The dual worker pattern is load-bearing.** TS and Python both instantiate a separate durable worker with default **1000 slots** versus **100** for the non-durable worker. Both share the same config (name, labels) but have distinct worker IDs and action registries. This is not mentioned in the document but is a real parity requirement.

5. **Python is a multi-process architecture.** The Python SDK uses a main worker process, a separate action listener process, and `ThreadPoolExecutor` for sync tasks. This is a Python-specific workaround for the GIL and is **exactly what Rust should NOT copy** — Rust's native async + `tokio::spawn_blocking` is the idiomatic analogue. The document correctly warns against copying Python patterns, but this specific case deserves explicit callout.

6. **Task output validation rules are real.** Both SDKs reject outputs containing `\u0000` because Postgres cannot store them, and cap payload sizes. A Rust SDK must implement these same validations in the serde serialization path.

7. **The `WaitFor` condition system has a real type hierarchy.** `UserEventCondition(key, expr)`, `SleepCondition(duration)`, `ParentCondition(task, expr)`, plus `AndCondition`/`OrCondition` combinators. The underlying proto is `BaseMatchCondition` + specialized variants (`SleepMatchCondition`, `UserEventMatchCondition`, etc.). The Rust design needs a proper sum-type enum here, not just strings.

8. **The TS SDK uses `nice-grpc` + `axios` + `zod` + `semver`.** Zod provides optional runtime schema validation; semver is used for engine-version compatibility checks at client init. The Rust equivalents are `tonic` + `reqwest` + optional `schemars`/`validator` + `semver` crate. The compatibility check is non-optional for parity.

9. **The `DedupeViolationErr` is a distinct error type.** Triggered when `childKey` dedup is enabled and duplicate key is used. The Rust `HatchetError` enum needs a dedicated variant.

10. **Rate limiting is dual-mode: static and dynamic (CEL).** Both TS and Python support this. Any Rust `RateLimit` type must accept either a static limit or a CEL expression.

## Where the document's claims need sharpening

| Document claim                                                   | Reality                                                                                                                                                                                                                          | What to change                                                                                                                             |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| "Go exposes `OnFailure` but not clearly `OnSuccess`"             | Go has **only** `OnFailure` at workflow/standalone-task level. `OnSuccess` is TS/Python only.                                                                                                                                    | Call out explicitly that `OnSuccess` is a TS/Python-only feature, making it optional for v1 Rust parity.                                   |

## Phase 1 — `hatchet-core`: shared types

**Goal:** every type used by transport, worker, and public API that is not a client or a runtime concept.

**Required modules:**

1. `ids.rs` — typed newtype wrappers: `TenantId`, `WorkflowId`, `WorkflowVersionId`, `WorkflowRunId`, `TaskId`, `TaskRunId`, `StepRunId`, `WorkerId`, `EventId`, `ScheduleId`, `CronId`, `RateLimitKey`. All serialize as strings, derive `Debug`, `Clone`, `Eq`, `Hash`, `Serialize`, `Deserialize`. Use a macro to avoid boilerplate.

2. `duration.rs` — `DurationSpec` type that parses Go-style duration strings (`"5s"`, `"10m"`, `"1h30m"`, `"500ms"`). Accepts `ns`, `us`, `µs`, `ms`, `s`, `m`, `h`. Provide `From<std::time::Duration>`, `From<chrono::Duration>`, `FromStr`, `Display`, `Serialize`, `Deserialize`. This is load-bearing: **Go duration strings are the wire format for sleep conditions.**

3. `metadata.rs` — `Metadata` = `BTreeMap<String, String>`. Type alias plus helper constructor macro.

4. `run_opts.rs` — `RunOpts` struct (derive_builder). Fields exactly matching TS `RunOpts` plus Go `RunOptFunc`:
    - `metadata: Metadata`
    - `priority: Option<RunPriority>` where `RunPriority = i32` with constants `LOW=1, MEDIUM=2, HIGH=3`
    - `sticky: bool`
    - `child_key: Option<String>`
    - `desired_worker_id: Option<String>`
    - `desired_worker_labels: BTreeMap<String, DesiredWorkerLabel>`
    - `return_exceptions: bool`
    - `trigger_at: Option<DateTime<Utc>>` (for scheduled runs)
    - `parent_workflow_run_id: Option<WorkflowRunId>` (for child runs)
    - `parent_step_run_id: Option<StepRunId>`

5. `labels.rs` — `WorkerLabels` = `BTreeMap<String, LabelValue>`. `LabelValue` is `enum { String(String), Integer(i64), Float(f64) }`. `DesiredWorkerLabel { value, required, weight, comparator }`. `WorkerLabelComparator` is `enum { Equal, NotEqual, GreaterThan, GreaterThanOrEqual, LessThan, LessThanOrEqual }`. Match the Go `types.StickyStrategy` constants (`SOFT`, `HARD`).

6. `conditions.rs` — the condition sum type. Match the Go public API verbatim:

    ```
    pub enum Condition {
      Sleep(DurationSpec),
      UserEvent { event_key: String, expression: Option<String> },
      Parent { task_ref: TaskRef, expression: Option<String> },
      And(Vec<Condition>),
      Or(Vec<Condition>),
    }
    ```

    Plus constructors `sleep_condition`, `user_event_condition`, `parent_condition`, `and_condition`, `or_condition`.

7. `concurrency.rs` — match the Go `types.Concurrency`: `{ Expression: String, MaxRuns: i32, LimitStrategy: ConcurrencyLimitStrategy }`. Strategy enum: `CancelInProgress`, `GroupRoundRobin`, `CancelNewest`.

8. `rate_limit.rs` — `RateLimit { key: String, units: i32, duration: DurationSpec }`. Plus CEL-expression variant `DynamicRateLimit { key_expr: String, units_expr: String, duration: DurationSpec }`.

9. `errors.rs` — `HatchetError` enum:
    - `Config(String)`
    - `Transport(TransportError)` (contains `tonic::Status` or `reqwest::Error`)
    - `Auth(String)`
    - `Serialization(serde_json::Error)`
    - `IllegalOutput(String)` — matches Python `IllegalTaskOutputError`
    - `DedupeViolation(String)` — matches TS `DedupeViolationErr`
    - `Cancelled`
    - `WorkflowNotFound(String)`
    - `RunNotFound(WorkflowRunId)`
    - `EngineVersion(String)` — capability drift
    - `Timeout`
    - `Other(String)`

    Plus `TaskError` enum used only inside handlers:
    - `Retry(Box<dyn std::error::Error + Send + Sync>)`
    - `NonRetryable(Box<dyn std::error::Error + Send + Sync>)`

    Implement `From<reqwest::Error>`, `From<tonic::Status>`, `From<serde_json::Error>`, `From<std::io::Error>`, `From<tokio::task::JoinError>`.

10. `output_validation.rs` — a single function `validate_output(bytes: &[u8]) -> Result<(), HatchetError>` that rejects any byte sequence containing `\x00` (the Postgres null-unicode issue). Call this on every serialized output in the worker before sending.

```rust
}

pub trait DurableContext: Context {
    fn invocation_count(&self) -> u32;
    async fn now(&self) -> Result<DateTime<Utc>, HatchetError>;     // replay-safe clock

    async fn sleep_for(&self, duration: DurationSpec, label: Option<&str>) -> Result<SleepResult, HatchetError>;
    async fn sleep_until(&self, wake_at: DateTime<Utc>) -> Result<SleepResult, HatchetError>;

    async fn wait_for(&self, conditions: Condition) -> Result<WaitMatches, HatchetError>;
    async fn wait_for_event<T: DeserializeOwned + Send + 'static>(
        &self, key: &str, expression: Option<&str>, scope: Option<&str>, lookback: Option<DurationSpec>

    async fn spawn_child<I, O>(&self, workflow: &WorkflowHandle<I, O>, input: I, opts: ChildRunOpts) -> Result<O, HatchetError>
    where I: Serialize + Send + 'static, O: DeserializeOwned + Send + 'static;

    where I: Serialize + Send + 'static, O: DeserializeOwned + Send + 'static;

    async fn signal(&self, key: &str, payload: serde_json::Value) -> Result<(), HatchetError>;  // Python compat
}
```

### 3.2 Context implementation types

Two concrete structs, `TaskContext` implementing `Context`, and `DurableTaskContext` implementing `DurableContext`. Both are constructed per task invocation by the worker runtime and carry:

- An `Arc<WorkerShared>` with the gRPC clients, action registry, cancellation token
- The `AssignedAction` proto message from the dispatcher
- An internal `ParentOutputCache` populated from the action's parent results
- For `DurableTaskContext`: an `Arc<DurableEventLog>` and `Mutex<MemoTable>` keyed by a stable operation index. Every durable op (sleep, wait_for, spawn) bumps the index. Replay-safe: on re-run, the memo table is rebuilt from the durable event log and returned operations don't re-issue against the engine.

### 3.3 Action handler erasure

```rust
type ErasedHandler = Arc<dyn ErasedFn + Send + Sync + 'static>;

trait ErasedFn {
    fn call(
        &self,
        input: Vec<u8>,
        ctx: Box<dyn ErasedContext>,
    ) -> Pin<Box<dyn Future<Output = Result<Vec<u8>, TaskError>> + Send>>;
}
```

When the user registers `fn(I, TaskContext) -> Fut<Output=Result<O, TaskError>>`, wrap it in a struct that implements `ErasedFn` by deserializing `input: Vec<u8>` via `serde_json::from_slice::<I>`, calling the real function, and serializing the output via `serde_json::to_vec(&output)`. Validate via `output_validation::validate_output` before returning.

All handlers are stored in `Arc<BTreeMap<ActionId, ErasedHandler>>` inside the worker. Action IDs are lowercase `{namespace}{workflow_name}:{task_name}`.

### 3.4 Worker runtime

```rust
pub struct Worker {
    name: String,
    slots: usize,               // default 100
    durable_slots: usize,       // default 1000
    labels: WorkerLabels,
    non_durable_registry: Arc<BTreeMap<ActionId, ErasedHandler>>,
    durable_registry: Arc<BTreeMap<ActionId, ErasedHandler>>,
    // two workers registered with engine: one non-durable, one durable
    inner: Arc<WorkerInner>,
}
```

`Worker::start()`:

1. Register both worker identities with the dispatcher via `Register` RPC (one call per). Receive `worker_id_non_durable` and `worker_id_durable`.
2. Spawn a heartbeat task for each worker: every **4 seconds**, call `Heartbeat` RPC. On failure, reconnect via `ListenV2`.
3. Spawn the action listener for each worker via `ListenV2` bidirectional stream. Fall back to `Listen` only if the engine rejects V2 (check `EngineVersion` capability).
4. For each `AssignedAction` received on the stream, look up the handler in the registry, build the appropriate `Context` or `DurableContext`, and spawn a `tokio::task` bounded by a semaphore sized to `slots` / `durable_slots`.
5. Handler task lifecycle:
    - Emit `STEP_EVENT_TYPE_STARTED` via `SendStepActionEvent` RPC.
    - Run the handler to completion with `tokio::select!` against a cancellation token.
    - On success: validate output, emit `STEP_EVENT_TYPE_COMPLETED` with the serialized JSON bytes.
    - On `TaskError::NonRetryable`: emit `STEP_EVENT_TYPE_FAILED` with `should_not_retry=true`.
    - On `TaskError::Retry`: emit `STEP_EVENT_TYPE_FAILED` with `should_not_retry=false`.
    - On panic: catch via `tokio::task::JoinHandle`, emit failed, run the user's panic handler if any.
6. On shutdown: call `Unsubscribe`, drain in-flight tasks with a configurable timeout.

### 3.5 Durable runtime specifics

The durable worker's handler wrapper additionally:

1. Reads the `AssignedAction`'s replay log.
2. Creates a `DurableTaskContext` with `invocation_count` derived from the number of prior invocations in the log.
3. Every call to `sleep_for`, `wait_for`, `wait_for_event`, `spawn_child` must:
    - Check the memo table for this operation index first. If present, return the memoized result.
    - If not present, issue the corresponding gRPC call (e.g., `CreateDurableEvent` for sleep, `WaitForEvent` for events) and `await` the callback via the durable listener.
    - Store the result in the memo table.
4. `now()` must return the timestamp recorded in the first invocation's memo entry on replay, never `chrono::Utc::now()`. This is the core replay-safety contract.

The durable listener itself is a separate long-lived gRPC stream handled inside the worker. It routes callbacks to the correct in-flight task via `(task_run_id, operation_index)`.

## Concrete instructions to the LLM that will execute this

When handing this plan to an LLM, append these execution rules:

1. **Read before writing.** For every phase, the LLM must read the listed source files from all three SDKs before producing any Rust code. It must summarize its understanding in a plan comment at the top of each Rust module it creates.
2. **Use the unofficial `hatchet-sdk` crate as a transport-scaffolding reference only.** Do not copy its API surface; it is an incomplete subset. Do copy: `build.rs` protoc setup, `Cargo.toml` dependency versions, TLS configuration, JWT token decoding.
3. **Never fabricate method names.** Every public method in the Rust API must correspond to a method verified to exist in either the TS, Go, or Python SDK source. If a method exists in only one SDK, document which one in a doc comment.
4. **Preserve the wire protocol exactly.** Action IDs are lowercase; durations are Go strings; heartbeat is 4s; bulk batch is 500; dual worker slots default to 100/1000; stream chunk indices are monotonic; payload threshold is 3MB.
5. **Every phase ends with tests.** The LLM must produce at least one unit test per module and one integration test per feature before starting the next phase. No phase advances without a green `cargo test` in that phase's scope.
6. **Document gaps, don't hide them.** If the LLM encounters a TS capability whose exact semantics cannot be reconstructed from the source, it must explicitly document the gap in a `TODO: parity-verify` comment and surface it in the PR description. Do not guess.
7. **Commit boundaries.** One commit per phase. Each commit's message references the specific SDK files read and includes the parity table entries being fulfilled.
8. **Cross-check with Python and Go.** For every TS-sourced method, check whether Python and Go implement it. If all three agree, the behavior is canonical. If they diverge, prefer TS semantics but document the divergence.

With this plan, a capable LLM with source-tree access and a Hatchet engine container should be able to produce a parity-level Rust SDK in roughly the phase order above, with the durable runtime (phase 3.5) as the critical gating milestone.
