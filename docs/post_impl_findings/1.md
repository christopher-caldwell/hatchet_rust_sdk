# Hatchet Rust SDK — TypeScript Parity Plan

## Scope and Objectives

This document is the canonical implementation roadmap for bringing the Hatchet Rust SDK to feature parity with the TypeScript v1 SDK. The goal is not a mechanical translation; Rust has different constraints around generics, async traits, ownership, and compile-time evaluation. Every design decision below chooses the idiomatic Rust equivalent of the TypeScript pattern, notes the exact gap, and provides code examples from both sides.

The phases are ordered by dependency: later phases build on earlier ones. Each phase identifies the exact files to change, the exact API shape to produce, and includes a complete runnable example that exercises only that phase's feature set.

---

## Guiding Rust Idioms

Before the phases, a set of principles that govern every API decision below.

**1. `impl Trait` over `dyn Trait` at call sites.** Handler closures and context arguments use `impl Context` / `impl DurableContext` rather than `Arc<dyn Context>`. This avoids boxing and preserves monomorphization. `dyn` is reserved for heterogeneous collections in the worker registry.

**2. Builder pattern for configuration.** Anywhere TypeScript uses an object literal (`{ retries: 3, timeout: '60s' }`), Rust uses a builder struct with owned fluent setters that terminates in `.build()` or is used inline. Config structs also implement `Default` so callers only set what they need.

**3. `async fn` in traits via `async_trait`.** Until `async fn in traits` is stable with the full feature set needed, `async_trait` is the pragmatic choice. All trait methods that are async are marked `#[async_trait]`.

**4. Typed generics, not `Value` at the surface.** JSON serialization happens inside the SDK, not at user call sites. User-facing methods take `I: Serialize` and return `O: DeserializeOwned`. The only `Value` visible to users is when they explicitly request raw JSON.

**5. Proc-macros for ergonomics only.** Macros generate boilerplate (task name constants, handle factories, registration functions) but do not hide types. The generated code is inspectable, and users can bypass macros if they prefer the builder API.

**6. Errors are typed, not boxed.** The SDK has a single `hatchet_sdk::Error` enum. `Result<T>` is `Result<T, hatchet_sdk::Error>` throughout.

## Phase 1 — `WorkflowHandle` API Correction

### Problem

In the TypeScript SDK:

```typescript
// Blocks until the workflow output is ready:
const output: O = await workflow.run(input, opts);

// Returns immediately with a handle for later polling:
const ref: WorkflowRunRef<O> = await workflow.runNoWait(input, opts);
```

In the current Rust SDK, both `run` and `run_no_wait` are identical — they call `transport.run_workflow` and return a `WorkflowRunRef<O>` that is nothing but a run ID wrapper. The `O` type parameter is cosmetic; calling `.output()` is impossible. A user looking at the signature of `run` expects to receive the workflow output, not a run handle.

```rust
// Current — both return the same thing, neither can produce output:
pub async fn run(&self, input: I, opts: RunOpts) -> Result<WorkflowRunRef<O>>
pub async fn run_no_wait(&self, input: I, opts: RunOpts) -> Result<WorkflowRunRef<O>>
```

### Target API

```rust
impl<T: Transport, I: Serialize + Send, O: DeserializeOwned + Send> WorkflowHandle<T, I, O> {
    /// Submit and block until the workflow produces output.
    /// Mirrors TypeScript's `workflow.run(input, opts)` -> `Promise<O>`.
    pub async fn run(&self, input: I, opts: RunOpts) -> Result<O>;

    /// Submit and return immediately with a handle for later polling.
    /// Mirrors TypeScript's `workflow.runNoWait(input, opts)` -> `Promise<WorkflowRunRef<O>>`.
    pub async fn run_no_wait(&self, input: I, opts: RunOpts) -> Result<WorkflowRunRef<O>>;

    /// Submit many inputs fire-and-forget.
    /// Mirrors TypeScript's `workflow.runManyNoWait(runs)` -> `Promise<WorkflowRunRef<O>[]>`.
    pub async fn run_many_no_wait(
        &self,
        inputs: impl IntoIterator<Item = I> + Send,
        opts: RunOpts,
    ) -> Result<Vec<WorkflowRunRef<O>>>;
}
```

### Why this requires a connected in-memory transport

For `run()` to block until output, the transport must be able to deliver a result to the caller after the worker executes the task. Currently the transport only records submitted runs in a `Vec` and the worker is completely separate. They need to be connected.

The architecture for in-memory:

1. `InMemoryTransport` gains a `pending: Arc<Mutex<HashMap<WorkflowRunId, oneshot::Sender<Result<Value>>>>>`. When `run_workflow` is called, it creates a `(tx, rx)` pair, stores `tx`, and passes `rx` back to `WorkflowHandle::run`.
2. `InMemoryTransport` gains an optional `inbox: Option<mpsc::Sender<IncomingRun>>`. When a worker calls `worker.connect(transport)`, it registers its mpsc receiver with the transport's inbox. When `run_workflow` is called, the transport sends the run to the inbox, and the worker dispatches it to the correct task handler.
3. After executing a task, `WorkerRuntime` calls `transport.resolve(run_id, result)` which completes the oneshot in `pending`.

This models the real gRPC architecture: client submits to server (transport), server routes to worker (inbox), worker completes and reports back (resolve), client receives result (oneshot).

### Transport trait additions

```rust
// crates/hatchet-sdk/src/transport.rs

#[async_trait]
pub trait Transport: Send + Sync + 'static {
    async fn run_workflow(
        &self,
        workflow_name: &str,
        input: Value,
        opts: RunOpts,
    ) -> Result<WorkflowRunId>;

    async fn run_workflows(
        &self,
        workflow_name: &str,
        inputs: Vec<Value>,
        opts: RunOpts,
    ) -> Result<Vec<WorkflowRunId>>;

    // New: register a channel to receive the result for this run_id.
    // Called by WorkflowHandle::run before submitting.
    async fn register_result_channel(
        &self,
        run_id: &WorkflowRunId,
    ) -> Result<oneshot::Receiver<Result<Value>>>;

    // New: resolve a pending result. Called by WorkerRuntime after task execution.
    async fn resolve_result(&self, run_id: &WorkflowRunId, result: Result<Value>);
}
```

`InMemoryTransport::register_result_channel` creates a oneshot pair, stores the `Sender`, and returns the `Receiver`. `InMemoryTransport::resolve_result` removes the `Sender` from the map and sends the result. The default no-op impls on the trait return an `Err` for the channel method, so real transports that use server-side polling don't need to implement these (they can use a different output retrieval path).

### Files to change

- `crates/hatchet-core/Cargo.toml` — add `tokio = { version = "1", features = ["sync"] }`
- `crates/hatchet-sdk/src/transport.rs` — add `pending` field to `InMemoryTransport`, implement `register_result_channel` / `resolve_result`
- `crates/hatchet-sdk/src/client.rs` — change `WorkflowHandle::run` to call `register_result_channel` and await output; change `run_no_wait` to not register a channel; remove `run_many` in favor of `run_many_no_wait`
- `crates/hatchet-sdk/src/worker.rs` — `WorkerRuntime::execute_non_durable` and `execute_durable` call `transport.resolve_result` after handler returns

### Example: `examples/features/src/bin/declare_and_run.rs`

```rust
// After Phase 1, this example demonstrates the correct run/run_no_wait distinction.

use hatchet_sdk::{Client, InMemoryTransport, RunOpts};
use serde::{Deserialize, Serialize};
use std::sync::Arc;

#[derive(Serialize)]
struct OrderInput { order_id: String, amount_cents: u64 }

#[derive(Deserialize)]
struct OrderOutput { confirmation_code: String }

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let transport = Arc::new(InMemoryTransport::new());
    let client = Client::new(Arc::clone(&transport));

    // Register a worker and task so the in-memory transport can route to it.
    let order_task = client.task::<OrderInput, OrderOutput>("commerce.process_order");
    let worker = client
        .worker("commerce-worker")
        .register_task(&order_task, |input: OrderInput, _ctx| async move {
            Ok(OrderOutput {
                confirmation_code: format!("CONF-{}", input.order_id),
            })
        })
        .build()
        .start()?;

    let checkout = client.workflow::<OrderInput, OrderOutput>("commerce.checkout");

    // run() blocks and returns the output directly — no handle unwrapping needed.
    let output: OrderOutput = checkout
        .run(OrderInput { order_id: "ord-1".into(), amount_cents: 9_99 }, RunOpts::default())
        .await?;
    println!("confirmed: {}", output.confirmation_code);

    // run_no_wait() returns a WorkflowRunRef immediately.
    let handle = checkout
        .run_no_wait(OrderInput { order_id: "ord-2".into(), amount_cents: 4_99 }, RunOpts::default())
        .await?;
    println!("submitted: {}", handle.run_id());

    worker.shutdown().await?;
    Ok(())
}
```

## Phase 2 — `WorkflowRunRef` Enhancement

### Problem

The TypeScript `WorkflowRunRef<T>` is a rich object:

```typescript
const ref = await workflow.runNoWait(input);

// Await output later:
const output: T = await ref.output;

// Stream step events:
for await (const event of await ref.stream()) { ... }

// Cancel or replay the run:
await ref.cancel();
await ref.replay();
```

The current Rust `WorkflowRunRef<O>` is:

```rust
pub struct WorkflowRunRef<O> {
    pub run_id: WorkflowRunId,
    _output: PhantomData<fn() -> O>,
}
```

It cannot retrieve output, stream events, cancel, or replay. The type parameter `O` is unused.

### Target API

```rust
// crates/hatchet-core/src/run.rs (or crates/hatchet-sdk/src/run_ref.rs)

pub struct WorkflowRunRef<O> {
    run_id: WorkflowRunId,
    // Set when created via run_no_wait. Absent for fire-and-forget with no channel.
    result_rx: Option<oneshot::Receiver<Result<Value>>>,
    // Shared client reference for cancel/replay/stream -- erased to avoid circular deps.
    client: Option<Arc<dyn RunControl + Send + Sync>>,
    _output: PhantomData<fn() -> O>,
}

impl<O> WorkflowRunRef<O> {
    pub fn run_id(&self) -> &WorkflowRunId { &self.run_id }
}

impl<O: DeserializeOwned + Send + 'static> WorkflowRunRef<O> {
    /// Block until the workflow produces output and return it.
    /// Mirrors TypeScript's `await ref.output`.
    pub async fn output(self) -> Result<O>;

    /// Cancel this workflow run.
    /// Mirrors TypeScript's `await ref.cancel()`.
    pub async fn cancel(self) -> Result<()>;

    /// Replay this workflow run, returning a new ref.
    /// Mirrors TypeScript's `await ref.replay()`.
    pub async fn replay(self) -> Result<WorkflowRunRef<O>>;

    /// Stream step run events for this workflow.
    /// Mirrors TypeScript's `for await (const e of await ref.stream())`.
    pub fn stream(self) -> impl futures::Stream<Item = Result<StreamEvent>> + Send;
}

/// impl IntoFuture so `handle.await?` is equivalent to `handle.output().await?`.
impl<O: DeserializeOwned + Send + 'static> IntoFuture for WorkflowRunRef<O> {
    type Output = Result<O>;
    type IntoFuture = Pin<Box<dyn Future<Output = Result<O>> + Send>>;

    fn into_future(self) -> Self::IntoFuture {
        Box::pin(self.output())
    }
}
```

### `RunControl` trait

`WorkflowRunRef` needs to call cancel/replay without depending directly on the full `Client` type (which is generic over `T: Transport`). The solution is a type-erased trait:

```rust
// crates/hatchet-sdk/src/transport.rs or a new file

#[async_trait]
pub trait RunControl: Send + Sync {
    async fn cancel_run(&self, run_id: &WorkflowRunId) -> Result<()>;
    async fn replay_run(&self, run_id: &WorkflowRunId) -> Result<WorkflowRunId>;
    async fn stream_run(
        &self,
        run_id: &WorkflowRunId,
    ) -> Box<dyn Stream<Item = Result<StreamEvent>> + Send + Unpin>;
}
```

`Client<T>` implements `RunControl` by delegating to `self.runs()`. When `WorkflowHandle::run_no_wait` creates a `WorkflowRunRef`, it passes `Arc::clone(&self.run_control)` (where `self.run_control: Arc<dyn RunControl>` is stored in `WorkflowHandle` or `Client`).

### `StreamEvent` type

```rust
// crates/hatchet-core/src/lib.rs

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct StreamEvent {
    pub run_id: WorkflowRunId,
    pub task_name: String,
    pub event_type: StreamEventType,
    pub payload: Option<Value>,
    pub timestamp: std::time::SystemTime,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum StreamEventType {
    TaskStarted,
    TaskCompleted,
    TaskFailed,
    WorkflowCompleted,
    WorkflowFailed,
    Streamed,
}
```

### Files to change

- `crates/hatchet-core/src/run.rs` — add `result_rx`, `client`, `IntoFuture` impl; add `StreamEvent` type
- `crates/hatchet-core/Cargo.toml` — add `futures = "0.3"`
- `crates/hatchet-sdk/src/client.rs` — implement `RunControl` for `Client<T>`; update `WorkflowHandle::run_no_wait` to pass `Arc<dyn RunControl>` into `WorkflowRunRef`
- `crates/hatchet-sdk/src/clients.rs` — `RunsClient::cancel`, `RunsClient::replay` implementations wired to transport

### Example: `examples/features/src/bin/run_ref.rs`

```rust
use hatchet_sdk::{Client, InMemoryTransport, RunOpts};
use serde::{Deserialize, Serialize};
use std::sync::Arc;

#[derive(Serialize)]
struct ReportInput { tenant_id: String }

#[derive(Deserialize)]
struct ReportOutput { rows: usize }

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let transport = Arc::new(InMemoryTransport::new());
    let client = Client::new(Arc::clone(&transport));
    let report_task = client.task::<ReportInput, ReportOutput>("reports.generate");
    let worker = client
        .worker("report-worker")
        .register_task(&report_task, |input: ReportInput, _ctx| async move {
            Ok(ReportOutput { rows: input.tenant_id.len() * 100 })
        })
        .build()
        .start()?;

    let report = client.workflow::<ReportInput, ReportOutput>("reports.monthly");

    // run_no_wait returns a WorkflowRunRef immediately.
    let handle = report
        .run_no_wait(ReportInput { tenant_id: "tenant-42".into() }, RunOpts::default())
        .await?;

    println!("submitted {}", handle.run_id());

    // .await on the handle via IntoFuture:
    let output: ReportOutput = handle.await?;
    println!("rows: {}", output.rows);

    // Or use .output() explicitly:
    let handle2 = report
        .run_no_wait(ReportInput { tenant_id: "tenant-99".into() }, RunOpts::default())
        .await?;
    let output2 = handle2.output().await?;
    println!("rows: {}", output2.rows);

    worker.shutdown().await?;
    Ok(())
}
```

## Phase 3 — Task Configuration

### Problem

The TypeScript SDK has rich per-task configuration:

```typescript
const task = client.task({
  name: 'api.call',
  executionTimeout: '60s',
  scheduleTimeout: '5m',
  retries: 3,
  backoff: { factor: 2, maxSeconds: 600 },
  rateLimits: [{ units: 1, limit: 100, duration: 'HOUR', key: 'api-key' }],
  desiredWorkerLabels: {
    'region': { value: 'us-east', required: true, weight: 10, comparator: 'EQUAL' },
  },
  concurrency: { expression: 'input.userId', maxRuns: 5, limitStrategy: 'CANCEL_IN_PROGRESS' },
});
```

The current Rust `TaskHandle<I, O>` carries only a `task_name: String`. There is no configuration surface at all. Every configuration field from the TS side is missing.

### Target: `TaskConfig` and updated `TaskHandle`

```rust
// crates/hatchet-core/src/task.rs (new file)

use std::time::Duration;

#[derive(Debug, Clone, Default)]
pub struct TaskConfig {
    pub execution_timeout: Option<Duration>,
    pub schedule_timeout: Option<Duration>,
    pub retries: u32,
    pub backoff: Option<BackoffConfig>,
    pub rate_limits: Vec<RateLimit>,
    pub desired_worker_labels: std::collections::BTreeMap<String, DesiredLabelConfig>,
    pub concurrency: Option<ConcurrencyConfig>,
    pub input_schema: Option<serde_json::Value>,
}

impl TaskConfig {
    pub fn builder() -> TaskConfigBuilder { TaskConfigBuilder::default() }
}

#[derive(Debug, Clone, Default)]
pub struct TaskConfigBuilder {
    inner: TaskConfig,
}

impl TaskConfigBuilder {
    pub fn execution_timeout(mut self, d: Duration) -> Self {
        self.inner.execution_timeout = Some(d); self
    }
    pub fn schedule_timeout(mut self, d: Duration) -> Self {
        self.inner.schedule_timeout = Some(d); self
    }
    pub fn retries(mut self, n: u32) -> Self {
        self.inner.retries = n; self
    }
    pub fn backoff(mut self, factor: f32, max_seconds: u32) -> Self {
        self.inner.backoff = Some(BackoffConfig { factor, max_seconds }); self
    }
    pub fn rate_limit(mut self, rl: RateLimit) -> Self {
        self.inner.rate_limits.push(rl); self
    }
    pub fn desired_label(mut self, key: impl Into<String>, config: DesiredLabelConfig) -> Self {
        self.inner.desired_worker_labels.insert(key.into(), config); self
    }
    pub fn concurrency(mut self, config: ConcurrencyConfig) -> Self {
        self.inner.concurrency = Some(config); self
    }
    pub fn build(self) -> TaskConfig { self.inner }
}

#[derive(Debug, Clone)]
pub struct BackoffConfig {
    pub factor: f32,
    pub max_seconds: u32,
}

#[derive(Debug, Clone)]
pub struct RateLimit {
    pub units: u32,
    pub limit: u32,
    pub duration: RateLimitDuration,
    pub key: RateLimitKey,
}

impl RateLimit {
    pub fn new(units: u32, limit: u32, duration: RateLimitDuration) -> Self {
        Self { units, limit, duration, key: RateLimitKey::None }
    }
    pub fn with_static_key(mut self, key: impl Into<String>) -> Self {
        self.key = RateLimitKey::Static(key.into()); self
    }
    pub fn with_dynamic_key(mut self, expression: impl Into<String>) -> Self {
        self.key = RateLimitKey::Dynamic(expression.into()); self
    }
}

#[derive(Debug, Clone, Default)]
pub enum RateLimitKey {
    #[default]
    None,
    Static(String),
    Dynamic(String),
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum RateLimitDuration {
    Second,
    Minute,
    Hour,
    Day,
    Week,
}

#[derive(Debug, Clone)]
pub struct DesiredLabelConfig {
    pub value: LabelValue,
    pub required: bool,
    pub weight: Option<i32>,
    pub comparator: Option<WorkerLabelComparator>,
}

impl DesiredLabelConfig {
    pub fn new(value: impl Into<LabelValue>) -> Self {
        Self { value: value.into(), required: false, weight: None, comparator: None }
    }
    pub fn required(mut self) -> Self { self.required = true; self }
    pub fn weight(mut self, w: i32) -> Self { self.weight = Some(w); self }
    pub fn comparator(mut self, c: WorkerLabelComparator) -> Self {
        self.comparator = Some(c); self
    }
}

#[derive(Debug, Clone, PartialEq)]
pub enum LabelValue {
    String(String),
    Int(i64),
    Bool(bool),
}

impl From<&str> for LabelValue {
    fn from(s: &str) -> Self { LabelValue::String(s.to_owned()) }
}
impl From<String> for LabelValue {
    fn from(s: String) -> Self { LabelValue::String(s) }
}
impl From<i64> for LabelValue {
    fn from(i: i64) -> Self { LabelValue::Int(i) }
}
impl From<bool> for LabelValue {
    fn from(b: bool) -> Self { LabelValue::Bool(b) }
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum WorkerLabelComparator {
    Equal,
    NotEqual,
    GreaterThan,
    LessThan,
    GreaterThanOrEqual,
    LessThanOrEqual,
}

#[derive(Debug, Clone)]
pub struct ConcurrencyConfig {
    /// CEL expression evaluated against input to produce the concurrency key.
    pub expression: String,
    pub max_runs: u32,
    pub limit_strategy: ConcurrencyLimitStrategy,
}

impl ConcurrencyConfig {
    pub fn new(expression: impl Into<String>) -> Self {
        Self {
            expression: expression.into(),
            max_runs: 1,
            limit_strategy: ConcurrencyLimitStrategy::default(),
        }
    }
    pub fn max_runs(mut self, n: u32) -> Self { self.max_runs = n; self }
    pub fn limit_strategy(mut self, s: ConcurrencyLimitStrategy) -> Self {
        self.limit_strategy = s; self
    }
}

#[derive(Debug, Clone, Copy, Default, PartialEq, Eq)]
pub enum ConcurrencyLimitStrategy {
    #[default]
    QueueNewRuns,
    CancelInProgress,
    CancelOldest,
    GroupRoundRobin,
}
```

## Phase 4 — Workflow Declaration System

### Problem

In TypeScript, a workflow is a first-class declaration with triggers, concurrency, defaults, and a DAG of steps:

```typescript
const checkout = client.workflow<CheckoutInput, CheckoutResult>({
  name: 'commerce.checkout',
  on: { cron: '0 2 * * *', event: ['order:created'] },
  concurrency: { expression: 'input.tenant_id', maxRuns: 10 },
  defaultPriority: Priority.HIGH,
  taskDefaults: { retries: 2, executionTimeout: '30s' },
})
  .step(validatePayment, { name: 'validate' })
  .step(chargeCard, { name: 'charge', parents: [validatePayment] })
  .onFailure(notifyFailure)
  .onSuccess(sendConfirmation);
```

In the current Rust SDK, `#[workflow]` is only a module grouping macro. There is no way to declare triggers, concurrency, task defaults, or DAG edges. Users cannot tell the Hatchet engine "run this workflow on a cron" or "charge can only run after validate."

### Target: `WorkflowDeclaration<I, O>` builder

The Rust design uses a builder because:
1. Workflow config has optional fields with non-trivial types — a struct literal would require filling many `None`s.
2. The DAG step list is ordered and benefits from chaining (`.step()` accumulates into a `Vec`).
3. Builders are inspectable and testable as regular Rust values.

```rust
// crates/hatchet-sdk/src/workflow.rs (new file)

pub struct WorkflowDeclaration<I, O> {
    pub name: String,
    pub on_crons: Vec<String>,
    pub on_events: Vec<String>,
    pub concurrency: Option<ConcurrencyConfig>,
    pub default_priority: Option<Priority>,
    pub task_defaults: TaskConfig,
    pub sticky: Option<StickyStrategy>,
    pub steps: Vec<WorkflowStep>,
    _io: PhantomData<fn(I) -> O>,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum StickyStrategy { Soft, Hard }

pub struct WorkflowStep {
    pub task_name: String,
    pub config: TaskConfig,
    pub parents: Vec<String>, // task names this step waits for
}

impl<I: Serialize + Send + 'static, O: DeserializeOwned + Send + 'static>
    WorkflowDeclaration<I, O>
{
    pub fn new(name: impl Into<String>) -> Self { ... }

    /// Add a cron trigger. Multiple calls accumulate.
    /// Mirrors TypeScript's `on: { cron: '0 * * * *' }` / `onCrons`.
    pub fn on_cron(mut self, expr: impl Into<String>) -> Self;

    /// Add an event trigger. Multiple calls accumulate.
    /// Mirrors TypeScript's `on: { event: ['order:created'] }` / `onEvents`.
    pub fn on_event(mut self, key: impl Into<String>) -> Self;

    pub fn concurrency(mut self, config: ConcurrencyConfig) -> Self;
    pub fn default_priority(mut self, p: Priority) -> Self;
    pub fn task_defaults(mut self, config: TaskConfig) -> Self;
    pub fn sticky(mut self, strategy: StickyStrategy) -> Self;

    /// Add a step (task) to this workflow.
    pub fn step<SI, SO>(mut self, task: &TaskHandle<SI, SO>, config: TaskConfig) -> Self;

    /// Add a step with explicit parent dependencies.
    /// Mirrors TypeScript's `.step(task, { parents: [otherTask] })`.
    pub fn step_after<SI, SO>(
        mut self,
        task: &TaskHandle<SI, SO>,
        parents: &[&TaskHandle<SI, SO>],
        config: TaskConfig,
    ) -> Self;
}
```

## Phase 5 — Context Expansion

### Problem

The TypeScript `Context<T>` has approximately 25 methods. The current Rust `Context` trait has 8. The missing methods are not edge cases — they are core to building non-trivial workflows:

```typescript
// TypeScript -- all on ctx:
const prev = await ctx.parentOutput<ValidateResult>('validate_payment');
const meta = ctx.additional_metadata();
const retry = ctx.retry_count();
await ctx.logger.info('processing order', { orderId: input.order_id });
await ctx.refreshTimeout('30s');
await ctx.releaseSlot();
await ctx.worker.upsertLabels({ busy: 'true' });
const child = await ctx.runChild(childWorkflow, childInput, { sticky: true });
```

None of these are available in the current Rust Context.

### Target `Context` trait

Because Rust's async_trait does not support object-safe generic methods well, the Context trait is split:
- `Context` — the object-safe core (JSON methods, scalars, no generics)
- `ContextExt` — a blanket-impl extension trait with typed generic methods for ergonomics

## Phase 6 — Condition System and `DurableContext` Expansion

### Problem

The TypeScript `DurableContext` has a rich condition-based waiting system:

```typescript
// Wait for a specific user event with a CEL filter:
const payload = await ctx.waitForEvent('order:paid', 'input.order_id == event.order_id');

// Wait for the first of: a sleep OR an event:
await ctx.waitFor(Or(
  { sleepFor: '5m' },
  { eventKey: 'order:cancelled', expression: 'input.order_id == event.order_id' },
));

// Deterministic memoization (same value returned on replay):
const processedAt = await ctx.memo('processed_at', () => new Date());
```

The current Rust `DurableContext` has only `sleep_for`, `sleep_until`, and a primitive `wait_for_event` with a timeout. There is no condition composition, no CEL expression plumbing, no memoization, and `now()` reads the real wall clock (non-deterministic on replay).

### Target: `Condition` type

```rust
// crates/hatchet-core/src/condition.rs (new file)

#[derive(Debug, Clone)]
pub enum Condition {
    SleepFor(std::time::Duration),
    SleepUntil(std::time::SystemTime),
    Event(EventCondition),
}

#[derive(Debug, Clone, Default)]
pub struct EventCondition {
    pub event_key: String,
    /// CEL expression evaluated against `{ input: ..., event: ... }`.
    /// Plumbed to the engine; not evaluated in-memory.
    pub expression: Option<String>,
    pub scope: Option<String>,
    pub lookback_window: Option<std::time::Duration>,
    pub readable_data_key: Option<String>,
}

impl Condition {
    pub fn sleep_for(d: std::time::Duration) -> Self { Condition::SleepFor(d) }
    pub fn sleep_until(at: std::time::SystemTime) -> Self { Condition::SleepUntil(at) }
    pub fn event(key: impl Into<String>) -> EventConditionBuilder {
        EventConditionBuilder { key: key.into(), ..Default::default() }
    }
}

#[derive(Default)]
pub struct EventConditionBuilder {
    key: String,
    expression: Option<String>,
    scope: Option<String>,
    lookback_window: Option<std::time::Duration>,
    readable_data_key: Option<String>,
}

impl EventConditionBuilder {
    pub fn expression(mut self, expr: impl Into<String>) -> Self {
        self.expression = Some(expr.into()); self
    }
    pub fn scope(mut self, s: impl Into<String>) -> Self {
        self.scope = Some(s.into()); self
    }
    pub fn lookback(mut self, w: std::time::Duration) -> Self {
        self.lookback_window = Some(w); self
    }
    pub fn build(self) -> Condition {
        Condition::Event(EventCondition {
            event_key: self.key,
            expression: self.expression,
            scope: self.scope,
            lookback_window: self.lookback_window,
```

```rust
#[async_trait]
pub trait DurableContext: Context {
    fn invocation_count(&self) -> u32;
    fn supports_eviction(&self) -> bool { false }

    /// Memoized current time. Returns the same instant on every replay.
    /// Mirrors TypeScript's `await ctx.now()`.
    async fn now(&self) -> Result<std::time::SystemTime>;

    /// Sleep. On replay, skipped if already completed.
    async fn sleep_for(&self, duration: std::time::Duration) -> Result<SleepResult>;
    async fn sleep_until(&self, at: std::time::SystemTime) -> Result<SleepResult>;

    /// Wait for the first of one or more conditions.
    /// Mirrors TypeScript's `await ctx.waitFor(conditions)`.
    async fn wait_for(
        &self,
        conditions: impl Into<Conditions> + Send,
    ) -> Result<ConditionOutput>;

    /// Convenience wrapper for a single event condition.
    /// Mirrors TypeScript's `await ctx.waitForEvent(key, expression?, ...)`.
    async fn wait_for_event(&self, condition: EventCondition) -> Result<serde_json::Value>;

    /// Memoize a computation across replays.
    /// On first call: runs `f`, serializes the result, stores it.
    /// On subsequent calls (replay): returns the stored value without calling `f`.
    /// Mirrors TypeScript's `await ctx.memo('key', () => computation())`.
    async fn memo<T, F, Fut>(&self, key: &str, f: F) -> Result<T>
    where
        T: serde::Serialize + serde::de::DeserializeOwned + Send + 'static,
        F: FnOnce() -> Fut + Send,
        Fut: std::future::Future<Output = Result<T>> + Send;

    // Child workflow execution (blocks until output):
    async fn spawn_child_json(
        &self,
        workflow_name: &str,
        input: serde_json::Value,
        opts: RunOpts,
    ) -> Result<serde_json::Value>;

    async fn spawn_children_json(
        &self,
        workflow_name: &str,
        inputs: Vec<serde_json::Value>,
        opts: RunOpts,
    ) -> Result<Vec<serde_json::Value>>;
}
```

```rust
async fn memo<T, F, Fut>(&self, key: &str, f: F) -> Result<T>
where
    T: Serialize + DeserializeOwned + Send + 'static,
    F: FnOnce() -> Fut + Send,
    Fut: Future<Output = Result<T>> + Send,
{
    {
        let store = self.memo_store.read().await;
        if let Some(v) = store.get(key) {
            return Ok(serde_json::from_value(v.clone())?);
        }
    }
    let result = f().await?;
    let val = serde_json::to_value(&result)?;
    self.memo_store.write().await.insert(key.to_owned(), val);
    Ok(result)
}
```

```rust
                    .await?;

                ctx.log(LogLevel::Info, &format!("waiting for payment key={idem_key}")).await?;

                // Wait for payment event OR 15-minute timeout.
                let outcome = ctx
                    .wait_for(or([
                        Condition::event("payment:received")
                            .expression("input.order_id == event.order_id")
                            .build(),
                        Condition::sleep_for(Duration::from_secs(15 * 60)),
                    ]))
                    .await?;

                let status = if outcome.payload.is_some() { "paid" } else { "timed_out" };
                Ok(OrderOutput { final_status: status.into() })
            },
        )
        .build()
        .start()?;

    let (result, _) = tokio::join!(
        client
            .workflow::<OrderInput, OrderOutput>("orders.wait_for_payment")
            .run(OrderInput { order_id: "ord-1".into() }, RunOpts::default()),
        async {
            tokio::time::sleep(Duration::from_millis(50)).await;
            transport_clone
                .emit_durable_event(
                    "payment:received",
                    serde_json::json!({ "order_id": "ord-1" }),
                )
                .await
        },
    );

    println!("status: {}", result?.final_status);
    worker.shutdown().await?;
    Ok(())
}
```

## Phase 7 — Worker Runtime: Labels Routing, Pause/Resume, SIGINT

### Problem

TypeScript worker supports label-based task routing, pause/resume, and graceful SIGINT shutdown:

```typescript
await worker.upsertLabels({ region: 'us-east', gpu: 'true' });
await worker.pause();
await worker.unpause();
worker.stop(); // called automatically on SIGINT
```

The Rust worker has labels in `WorkerBuilder` but they don't affect task routing. There is no pause/resume and no signal handling.

### Target API additions to `WorkerHandle`

```rust
impl WorkerHandle {
    pub async fn shutdown(self) -> Result<()>;
    pub async fn pause(&self) -> Result<()>;
    pub async fn unpause(&self) -> Result<()>;
    pub async fn is_paused(&self) -> bool;
    pub async fn upsert_labels(
        &self,
        labels: impl IntoIterator<Item = (String, LabelValue)>,
    ) -> Result<()>;
    pub async fn labels(&self) -> BTreeMap<String, LabelValue>;
}
```

### Label routing in `WorkerRuntime`

When an incoming run specifies `desired_worker_labels`, `WorkerRuntime` checks its labels against each `DesiredLabelConfig`:

```rust
fn labels_match(
    worker_labels: &BTreeMap<String, LabelValue>,
    desired: &BTreeMap<String, DesiredLabelConfig>,
) -> bool {
    for (key, config) in desired {
        match worker_labels.get(key) {
            None if config.required => return false,
            Some(actual) => {
                if !compare_label(actual, &config.value, config.comparator) {
                    if config.required { return false; }
                }
            }
            _ => {}
        }
    }
    true
}
```

If the labels don't match, the runtime sends a routing failure back to the transport so it can retry with a different worker.

### SIGINT handler

In `Worker::start()`, spawn a task that listens for Ctrl-C and sends the shutdown work item:

```rust
let tx_clone = tx.clone();
tokio::spawn(async move {
    if tokio::signal::ctrl_c().await.is_ok() {
        let _ = tx_clone.send(WorkItem::Shutdown).await;
    }
});
```

### Files to change

- `crates/hatchet-sdk/src/worker.rs` — add `WorkItem::Pause`, `WorkItem::Unpause`, `WorkItem::UpsertLabels(BTreeMap<...>)`; add `paused: Arc<AtomicBool>` to `WorkerRuntime`; add label matching logic in `execute_non_durable`; add SIGINT spawn; add new `WorkerHandle` methods
- `crates/hatchet-sdk/src/context.rs` — `InMemoryContext::upsert_worker_labels` sends `WorkItem::UpsertLabels` via a back-channel stored in context
- `crates/hatchet-sdk/Cargo.toml` — add `tokio = { features = ["signal"] }`

### Example: `examples/features/src/bin/worker_runtime.rs`

```rust
use hatchet_sdk::{Client, Context, InMemoryTransport, LabelValue, RunOpts};
use serde::{Deserialize, Serialize};
use std::sync::Arc;

#[derive(Serialize, Deserialize)]
struct JobInput { id: String }

#[derive(Serialize, Deserialize)]
struct JobOutput { processed: bool }

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let transport = Arc::new(InMemoryTransport::new());
    let client = Client::new(Arc::clone(&transport));
    let job_task = client.task::<JobInput, JobOutput>("jobs.process");

    let handle = client
        .worker("job-worker")
        .labels([("region".into(), LabelValue::String("us-east".into()))])
        .register_task(&job_task, |input: JobInput, ctx: impl Context| async move {
            ctx.upsert_worker_labels(
                [("busy".into(), LabelValue::Bool(true))].into()
            ).await?;
            let out = JobOutput { processed: true };
            ctx.upsert_worker_labels(
                [("busy".into(), LabelValue::Bool(false))].into()
            ).await?;
            Ok(out)
        })
        .build()
        .start()?;

    handle.pause().await?;
    println!("paused: {}", handle.is_paused().await);
    handle.unpause().await?;

    handle.upsert_labels([("version".into(), LabelValue::String("v2".into()))]).await?;
    println!("labels: {:?}", handle.labels().await);

    let out = client
        .workflow::<JobInput, JobOutput>("jobs.process")
        .run(JobInput { id: "j-1".into() }, RunOpts::default())
        .await?;

    println!("processed: {}", out.processed);
    handle.shutdown().await?;
    Ok(())
}
```

## Phase 8 — Feature Clients: Full Implementations

### Problem

Most feature clients are stubs with no real in-memory behavior. Critical gaps:

- `client.events().push(key, payload)` — needed for durable event workflows; currently absent
- `client.crons()` — create/delete/list/trigger; currently stubs
- `client.scheduled()` — create/delete/list/trigger; currently stubs

### `EventsClient`

```rust
#[async_trait]
pub trait EventsClientTrait: Send + Sync {
```

## Phase 9 — `RunOpts` Restructure

### Problem

`RunOpts` currently uses `metadata: HashMap<String, Value>` where TypeScript uses `additionalMetadata: Record<String, String>` (string values only). More importantly, the parent linkage fields that the current SDK stuffs into `metadata` as arbitrary JSON map entries should be first-class struct fields:

```rust
// Current -- parent linkage buried in freeform metadata:
opts.metadata.insert("parent_workflow_run_id", json!(parent_id.to_string()));
opts.metadata.insert("parent_task_run_id", json!(task_run_id));
opts.metadata.insert("child_index", json!(idx));
```

These correspond to dedicated protobuf fields in the real Hatchet wire protocol. Stuffing them in a map makes them invisible to transport implementations and breaks introspection.

### Target `RunOpts`

```rust
// crates/hatchet-core/src/run.rs

#[derive(Debug, Clone, Default)]
pub struct RunOpts {
    /// Arbitrary string metadata attached to this run.
    /// Mirrors TypeScript's `additionalMetadata`.
    pub additional_metadata: std::collections::HashMap<String, String>,
    pub priority: Option<Priority>,
    /// Route this run to the same worker that ran the parent.
    pub sticky: bool,
    /// Deduplication key. Mirrors TypeScript's `childKey`.
    pub child_key: Option<String>,
    pub desired_worker_labels: std::collections::BTreeMap<String, DesiredLabelConfig>,
    // First-class parent linkage (not stuffed into metadata).
    pub parent_workflow_run_id: Option<WorkflowRunId>,
    pub parent_task_run_id: Option<String>,
    pub child_index: Option<u64>,
}
```

### Files to change

- `crates/hatchet-core/src/run.rs` — replace `metadata: HashMap<String, Value>` with the above
- `crates/hatchet-sdk/src/context.rs` — `child_run_opts` sets struct fields directly, not metadata entries
- `examples/features/src/bin/context_child_runs.rs` — update verification to check `opts.parent_workflow_run_id.is_some()` instead of `opts.metadata.contains_key(...)`

## Phase 10 — Input Validation

### Problem

TypeScript uses Zod to validate workflow input at the point of dispatch, giving users immediate clear errors instead of confusing deserialization failures inside handlers:

```typescript
const wf = client.workflow({
  name: 'my-wf',
  inputValidator: z.object({ name: z.string(), age: z.number().positive() }),
});
```

The Rust SDK has no equivalent. A handler that receives malformed JSON panics or returns an opaque deserialization error from inside the task.

### Target: `schemars` + `jsonschema`

Derive JSON Schema from the input type using `schemars`, store it in `TaskConfig`, and validate at dispatch time in `WorkerRuntime`:

```rust
// User's input type opts in with a derive:
#[derive(Serialize, Deserialize, schemars::JsonSchema)]
struct OrderInput {
    order_id: String,
    amount_cents: u64,
}

// TaskConfig stores the schema:
TaskConfig::builder()
    .with_input_schema::<OrderInput>()
    .build()

// WorkerRuntime validates before calling handler:
if let Some(schema) = &config.input_schema {
    let compiled = jsonschema::JSONSchema::compile(schema)?;
    if !compiled.is_valid(&raw_input) {
        let errors: Vec<_> = compiled.validate(&raw_input)
            .unwrap_err()
            .map(|e| e.to_string())
            .collect();
        reply.send(Err(Error::InputValidation(errors))).ok();
        return;
    }
}
```

The `#[task(validate_input)]` macro attribute enables this automatically:

```rust
#[task(validate_input)]
pub async fn process_order(input: OrderInput, ctx: impl Context) -> Result<OrderOutput> {
    // Input is guaranteed to be valid here.
    todo!()
}
```

The macro adds `.with_input_schema::<OrderInput>()` to the generated `TaskConfig`.

### Files to change

- `crates/hatchet-core/Cargo.toml` — add `schemars = { version = "0.8", optional = true }`; feature `input-validation`
- `crates/hatchet-sdk/Cargo.toml` — add `jsonschema = { version = "0.17", optional = true }`; feature `input-validation`
- `crates/hatchet-core/src/task.rs` — add `input_schema: Option<Value>` to `TaskConfig`; add `with_input_schema<I: JsonSchema>()` method behind feature flag
- `crates/hatchet-sdk/src/worker.rs` — validate in `execute_non_durable` / `execute_durable` when schema is present
- `crates/hatchet-macros/src/lib.rs` — parse `validate_input` attribute

## Phase 11 — Proc Macro Handler Signatures

### Problem

Current macro output locks handlers to `InMemoryContext<T>`:

```rust
// User must write:
pub async fn my_task(input: MyInput, ctx: InMemoryContext<T>) -> Result<MyOutput>
```

After Phase 5, handlers should take `impl Context` (ergonomic) or `Ctx: Context` (explicit):

```rust
// Target:
pub async fn my_task(input: MyInput, ctx: impl Context) -> Result<MyOutput>
```

### Macro rewrite strategy

In Rust stable, `impl Trait` in function argument position in a non-closure function is syntactic sugar for an anonymous generic parameter. The macro can detect `impl Context` or `impl DurableContext` in the second argument and rewrite the function to add an explicit generic parameter. This is transparent to users and compiles correctly on stable Rust:

**User writes:**

```rust
#[task]
pub async fn charge_card(input: OrderInput, ctx: impl Context) -> Result<OrderOutput> { ... }
```

**Macro rewrites to:**

```rust
pub async fn charge_card<__Ctx: Context + Send>(input: OrderInput, ctx: __Ctx) -> Result<OrderOutput> { ... }
```

The generated `register_all` still calls `builder.register_task(&handle, charge_card)`, where `charge_card` is now a generic function that the compiler monomorphizes to `InMemoryContext<T>` at the registration call site.

### `function_signature_types` update

The existing validator must be relaxed: instead of requiring the second argument to be a specific concrete type like `InMemoryContext<T>`, it accepts:
1. `impl Context` / `impl DurableContext` (rewrite to generic)
2. Any concrete type that the user chose (preserve as-is, let compiler catch errors)
3. Still validates async, 2 args, `Result<T>` return

### Files to change

- `crates/hatchet-macros/src/lib.rs` — detect `impl Context` / `impl DurableContext` in arg 2 and emit a generic parameter; update `function_signature_types` to not require specific concrete type
- All examples using `#[task]` or `#[durable_task]` — update handler signatures from `ctx: InMemoryContext<_>` to `ctx: impl Context`

## Phase 12 — `NonRetryableError` and Error Taxonomy

### Problem

TypeScript has `NonRetryableError` to skip retries immediately:

```typescript
import { NonRetryableError } from '@hatchet-dev/typescript-sdk';

if (input.invalid) {
  throw new NonRetryableError('bad input');
}
```

The Rust SDK has a flat `Error` enum with no retry semantics. Any `Err(...)` from a handler triggers a retry if `retries > 0`, even for errors that should be fatal.

### Target

```rust
// crates/hatchet-core/src/error.rs

#[derive(Debug, thiserror::Error)]
pub enum Error {
    #[error("serialization: {0}")]
    Serialization(String),
    #[error("deserialization: {0}")]
    Deserialization(String),
    #[error("worker: {0}")]
    Worker(String),
    #[error("durable: {0}")]
    Durable(String),
    #[error("input validation: {0:?}")]
    InputValidation(Vec<String>),
    /// Returning this bypasses retries.
    /// Mirrors TypeScript's `throw new NonRetryableError(message)`.
    #[error("non-retryable: {0}")]
    NonRetryable(String),
    #[error("dedupe violation: {0}")]
    DedupeViolation(String),
}

impl Error {
    pub fn non_retryable(msg: impl Into<String>) -> Self {
        Error::NonRetryable(msg.into())
    }

    pub fn is_retryable(&self) -> bool {
        !matches!(
            self,
            Error::NonRetryable(_) | Error::InputValidation(_) | Error::DedupeViolation(_)
        )
    }
}
```

`WorkerRuntime` checks `error.is_retryable()` before scheduling a retry.

### Files to change

- `crates/hatchet-core/src/error.rs` (or `lib.rs`) — update `Error` enum with new variants
- `crates/hatchet-sdk/src/worker.rs` — check `is_retryable()` in retry logic
- `crates/hatchet-sdk/src/lib.rs` — re-export `Error::non_retryable`

## What Is Explicitly Deferred

The following TypeScript features require a real gRPC/REST transport to be meaningful. The API surface (struct fields, method stubs) is added during the phases above, but in-memory behavior is a no-op:

- **CEL expression evaluation** — `ConcurrencyConfig.expression`, `EventCondition.expression`, rate limit dynamic keys. Fields are plumbed; evaluation requires connecting to the Hatchet server.
- **Real cron scheduling** — `CronsClient.create` stores the entry but does not fire it on schedule.
- **Engine version detection** — `supports_eviction()` returns `false` until a server connection reports the engine version.
- **Middleware** — TypeScript has `MiddlewareBefore`/`MiddlewareAfter` type params on `HatchetClient`. Rust's equivalent is a tower-style service layer; deferred until the gRPC transport layer.
- **`put_stream` consumption** — The in-memory transport is a no-op receiver; streaming output requires a real server.
- **Legacy workflow compatibility** — TypeScript Worker handles `LegacyWorkflow` for SDK version compatibility. Not applicable to a new Rust SDK.
