## Information Gaps Closed

### 1. OR waits no longer behave sequentially

Before this pass, Rust `wait_for(or([...]))` effectively walked the list in order. That was a behavioral mismatch with the TS SDK, where grouped conditions are intended to race and the first satisfied condition wins.

Closed gap:

- Rust now evaluates OR waits as concurrent pending conditions rather than linear branches.
- Sleep branches and event branches can compete in one wait.
- The returned `matched_condition_index` now reflects the condition that actually won the race.

Why this matters:

- This fixes the most important semantic bug in the prior in-memory durable runtime.
- It makes timeout-vs-event waits behave the way TS users expect.

### 2. Event lookback now checks durable event history

Before this pass, `lookback_window` was not acting like a real history lookup. It was effectively being reused as a timeout parameter for the wait path.

Closed gap:

- Rust now records observed durable events in an in-memory history log.
- Event waits with lookback search that history first.
- If a matching historical event exists inside the lookback window, the wait resolves immediately.

Why this matters:

- This closes one of the bigger semantic holes called out in `3.md` around durable event matching.
- It gives Rust a real notion of “consider prior events,” even though it is still local/in-memory.

### 3. Event scope is now honored in durable matching

Before this pass, Rust exposed a `scope` field on event conditions but did not have meaningful runtime enforcement behind it.

Closed gap:

- Rust now stores optional event scope metadata for emitted durable events.
- Event conditions with `.scope(...)` only match events with the same scope.
- Test coverage now exercises scoped historical event matching.

Why this matters:

- This narrows the discrepancy called out in `3.md` about richer scope semantics on event conditions.
- The feature is still in-memory, but the observable matching behavior is now closer to TS.

### 4. Event expression matching is materially better

Before this pass, the Rust expression path was narrow and had a bad fallback behavior: an event condition with an expression could still match even when the expression evaluated false.

Closed gap:

- False expressions no longer fall through to “match anyway.”
- Expression matching now supports dotted-path lookups instead of only flat `payload.foo`.
- The evaluator now accepts `payload.*`, `event.*`, `data.*`, or a bare dotted path.
- `null` literals are now supported, in addition to booleans, strings, integers, and floats.

Why this matters:

- This fixes a correctness bug, not just a convenience gap.
- It makes the in-memory evaluator more useful for TS-shaped event payload filters.

### 5. `readableDataKey` semantics are less wrong

Before this pass, Rust treated `readable_data_key` like a payload extraction key. That is not what the TS SDK means by `readableDataKey`.

Closed gap:

- Rust no longer uses `readable_data_key` to slice into the payload object.
- `ConditionOutput` now carries `matched_readable_data_key`.
- Event conditions default that matched key to the event key when no explicit readable key is supplied.

Why this matters:

- This is closer to the TS meaning of `readableDataKey` as condition identity/readability metadata.
- It removes a misleading API behavior in the old Rust implementation.

### 6. Replay-stable `now()` and basic memo storage remain present and verified

This work did not invent `memo` and `now`, but it preserved and verified the replay-stable local behavior while the wait semantics changed.

Confirmed behavior:

- `now()` remains memoized within the in-memory durable context.
- `memo()` still returns the stored value for a given key.
- The durable helper tests still pass after the runtime changes.

Why this matters:

- The durable semantics improved without regressing the earlier replay-stability work already landed in Rust.

## What This Work Did Not Close

This pass improved the durable runtime semantics, but it did not make the Rust SDK fully TS-equivalent in the conditions/runtime area.

### Still missing inside conditions and durable runtime

- TS-style `Action` metadata on conditions is still absent from Rust.
- Explicit `orGroupId` metadata still does not exist as a first-class Rust concept.
- Rust condition composition is still runtime-local; it is not transformed into engine protocol objects.
- Parent-condition parity is still missing.
- Durable eviction support is still missing.
- The wait/result shape is still Rust-local and not TS listener payload compatible.

### Still missing in runtime integration

- Durable events are still local to `InMemoryDurableContext`; they are not wired through a shared transport-backed listener channel.
- `wait_for` is still an in-memory wait implementation, not an engine-backed callback/listener round-trip.
- Cancellation is still not AbortController-like or listener-supervised.
- Replay/history stability is still shallow compared with TS engine semantics.

## Updated Bottom Line

The Rust SDK is closer to TS parity in one important area: durable wait semantics are no longer obviously wrong for OR waits, scoped events, lookback, and basic event-expression filtering.

The Rust SDK is still not at TS parity.

The remaining gap is no longer “durable waits exist but are mostly placeholders.” The remaining gap is narrower and more specific:

- the current durable runtime is still in-memory rather than listener/engine backed
- condition metadata is still not protocol-shaped
- eviction, cancellation supervision, and backend event integration are still missing

## Recommended Next Fix Order After This Pass

1. Move durable event observation off the local context and into shared transport/runtime plumbing.
2. Add protocol-shaped condition metadata in Rust: `action`, `or_group_id`, and readable identity fields.
3. Tighten `WorkflowRunRef` so stream/output semantics become listener-style rather than transport-snapshot based.
4. Add TS-style workflow creation helpers for `schedule`, `cron`, and default filter behavior.
5. Revisit validation parity with a derive-based Rust story instead of hand-written JSON schema fragments.
