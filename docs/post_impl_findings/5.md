## Findings From This Pass

### 1. Rust conditions now carry first-class metadata instead of treating it as implicit runtime trivia

Before this pass, Rust condition values only carried the minimum runtime fields needed for the in-memory waiter:

- sleep duration or wake time
- event key
- optional event expression / scope / lookback

That meant TS concepts like `action`, `orGroupId`, and readable identity did not really exist as part of the Rust condition model.

Closed gap:

- Rust now has `ConditionAction`.
- Rust now has `ConditionMetadata`.
- `Condition::SleepFor`, `Condition::SleepUntil`, and `Condition::Event` all carry metadata.
- Event builders can now set `action` and `or_group_id`, not just event-specific fields.
- Sleep conditions can now also carry `readable_data_key`, `action`, and `or_group_id` through fluent setters on `Condition`.

Why this matters:

- This is the first time Rust conditions are shaped like durable-condition objects rather than ad hoc runtime instructions.
- It is a prerequisite for wiring conditions into workflow declarations, transport payloads, and future engine-backed listeners.

### 2. OR groups now have explicit stable group metadata in Rust

Before this pass, Rust had an `or([...])` runtime helper, but the grouping concept only existed as execution behavior.

Closed gap:

- `or([...])` now assigns a concrete `or_group_id` onto each grouped condition.
- The grouped id is stored on the condition metadata itself rather than inferred only at wait time.

Why this matters:

- This is much closer to the TS `Or()` behavior, where grouped conditions share an explicit `orGroupId`.
- It separates “these conditions race together” from the current in-memory waiter implementation.

### 3. Rust now has a protocol-shaped condition renderer instead of only a runtime-local condition enum

Before this pass, Rust had no transformation layer analogous to TS `conditionsToPb(...)`.

Closed gap:

- Rust now exposes `render_conditions(...)`.
- Rust now exposes `conditions_to_rendered(...)`.
- Rust now has protocol-shaped structs:
  - `BaseMatchCondition`
  - `SleepMatchCondition`
  - `SleepUntilMatchCondition`
  - `UserEventMatchCondition`
  - `RenderedConditions`

What this currently does:

- applies default action metadata when rendering
- preserves explicit OR grouping
- computes readable identity fields
- preserves event expression, scope, and lookback metadata in the rendered output

Why this matters:

- This closes one of the specific parity gaps called out in `4.md`: Rust condition composition is no longer only runtime-local.
- The renderer is still Rust-local, but the condition data now has a transport/protocol-oriented shape that future integration code can consume.

### 4. `readableDataKey` behavior is now more TS-like for sleep conditions too

Before this pass, the prior work improved `readable_data_key` for event matches, but the broader condition model still did not treat readable identity as a first-class cross-condition concern.

Closed gap:

- Sleep conditions now also participate in readable identity metadata.
- Rendered sleep conditions default to a stable `sleep-*` readable key when none is provided.
- Event conditions continue to default readable identity to their event key.

Why this matters:

- This is closer to the TS condition base model, where readable identity is part of every condition’s base metadata, not just event wait output.

### 5. Test coverage now proves condition metadata survives render/transform steps

New test coverage explicitly verifies:

- default action propagation during render
- shared `or_group_id` across OR branches
- no implicit OR group on standalone conditions
- readable identity propagation into rendered protocol structs
- event scope retention in rendered conditions

## Relevant Current Context

This is the most important state-of-the-code observation after this pass:

### The new condition metadata layer exists, but it is still almost completely unconsumed

Today, the new types and helpers are present in:

- [`crates/hatchet-sdk/src/durable.rs`](file:///Users/christophercaldwell/Code/projects/rust/hatchet_rust_sdk/crates/hatchet-sdk/src/durable.rs)

But they are not yet wired into:

- workflow declarations in [`crates/hatchet-sdk/src/workflow.rs`](file:///Users/christophercaldwell/Code/projects/rust/hatchet_rust_sdk/crates/hatchet-sdk/src/workflow.rs)
- worker registration / scheduling paths
- transport payloads
- run listener / durable listener plumbing
- feature clients

That means the current result is best understood as:

- the condition model is now better shaped
- the runtime wait semantics remain in-memory
- the declaration / protocol / engine integration layers still do not consume the new shape

## What This Pass Narrowed But Did Not Close

### Mostly narrowed

- TS-style `Action` metadata on conditions
- explicit `orGroupId` support
- protocol-shaped condition transformation

These are no longer “missing entirely.” They now exist as Rust API/model pieces.

### Still open in practical parity terms

- workflow/task declarations still cannot express TS-style `waitFor`, `cancelIf`, and `skipIf` using the new condition layer
- rendered conditions are not converted to real protobuf or transport-backed request types
- parent-condition parity is still absent
- durable runtime still does not execute via shared listener/engine plumbing
- durable eviction and listener-supervised cancellation are still absent
- result payload shape from `wait_for` is still Rust-local, not TS listener-payload compatible

## Detailed Task List Of What Is Left To Finish

The remaining work is best split into four tracks. The ordering below is the recommended implementation order.

### 1. Integrate conditions into workflow/task declarations

Status: not started

Tasks:

1. Add declaration-level condition fields to workflow steps for TS-equivalent concepts:
   - `wait_for`
   - `cancel_if`
   - `skip_if`
2. Decide the idiomatic Rust API shape for declaration-time conditions:
   - likely `Conditions` or `Vec<Conditions>`
   - avoid copying TS overload patterns directly
3. Extend [`WorkflowStep`](file:///Users/christophercaldwell/Code/projects/rust/hatchet_rust_sdk/crates/hatchet-sdk/src/workflow.rs) so it stores condition declarations, not just parent task names and `TaskConfig`.
4. Add builder methods on `WorkflowDeclaration` for attaching conditions to steps.
5. Ensure OR-group metadata survives declaration construction unchanged.
6. Add tests for nested AND/OR declaration-time composition, mirroring the TS `Render(...)` cases that matter.

Why this should be next:

- Until declarations can carry the condition model, the new renderer is not connected to any real workflow API surface.

### 2. Add the missing condition types and finish the condition model

3. Revisit sleep-until rendering:

   - confirm whether this should stay Rust-local or be normalized before transport rendering
4. Tighten readable-key defaults to match TS semantics exactly where practical.
5. Expand tests to cover:
   - nested OR groups
   - custom explicit group ids

Why this matters:

- The condition layer is still incomplete relative to the TS hierarchy.

2. Add parent-condition support and finish the missing condition hierarchy pieces.

## Updated Bottom Line

The Rust SDK is closer to TS parity than it was in `4.md`, but the improvement in this pass is architectural rather than runtime-semantic.

What is now true:

- Rust conditions have first-class metadata.
- OR grouping is explicit in the Rust condition model.
- Rust can render conditions into a protocol-shaped structure.

What is still true:

- workflow declarations do not use the new condition layer
- transport/protocol code does not use the new rendered structures
- the durable runtime is still in-memory, not listener/engine backed

So the remaining gap is no longer “Rust has no condition metadata model.”

The remaining gap is:

- the condition model exists
- but it is not yet integrated into declaration, transport, and runtime execution paths
