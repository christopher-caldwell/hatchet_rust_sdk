# Hatchet Rust SDK vs TypeScript SDK: Remaining Discrepancies

This document is the working discrepancy list for the current Rust SDK parity pass.

Scope:

- The TypeScript SDK under `sources/hatchet-main/sdks/typescript/src/`
- The Rust SDK under `crates/hatchet-sdk/src/`
- The goal is not a mechanical 1:1 port. The goal is an idiomatic Rust API that matches the TS behavior where it matters.

This file records the concrete gaps that still exist after the current Rust implementation work.

## High-Level Parity Status

The Rust SDK now covers the common happy path:

- typed workflow handles
- typed task handles
- workflow run refs with `output`, `cancel`, `replay`, and `stream`
- worker runtime execution
- in-memory workflow declarations
- basic feature clients
- basic durable context helpers
- worker label routing and simple input validation

That said, it is still not at TS parity. The remaining gaps are mostly around runtime semantics, richer scheduling/declaration behavior, and the backend-oriented API surface that TS exposes.

## Concrete Missing Semantics

These are the specific behavioral mismatches that matter more than raw API shape:

- Workflow execution in Rust is in-memory and synchronous relative to the current test harness; TS is listener/dispatcher driven.
- Rust workflow declarations execute step graphs, but TS declarations are part of a richer engine protocol with orchestration and scheduling semantics.
- Rust run streaming is now backed by the transport, but TS streaming is event-based and carries step/run event structure.
- Rust durable waiting is functional for tests, but it is not a full durable engine contract.
- Rust input validation is basic JSON-schema style validation; TS uses Zod-derived schemas and richer typing.

## Recommended Next Fix Order

1. Finish the durable context contract around conditions, event matching, and replay stability.
2. Add TS-style workflow creation helpers that expose schedule/cron/default-filter semantics in idiomatic Rust.
3. Tighten `WorkflowRunRef` to better model listener-backed streams and eventual results.
4. Expand feature clients only where the current in-memory semantics can map cleanly to TS behavior.
5. Add a richer input-validation story, ideally with derive support instead of hand-written schema literals.

## Bottom Line

The Rust SDK is not yet full parity with the TS SDK.

It now matches the TS SDK well enough for:

- typed in-process workflow execution
- task dispatch
- child workflow helpers
- basic durable semantics
- in-memory feature client workflows

It still diverges from the TS SDK in the protocol-heavy and engine-heavy areas:

- listener-backed run/result streaming
- durable engine semantics
- richer workflow declaration and scheduling APIs
- full worker runtime supervision
- Zod-derived validation and middleware-aware typing

That is the remaining discrepancy list to drive the next round of work.

*Footnote: recommended next implementation steps*

1. Preserve the Rust API where it is already idiomatic, but add TS-equivalent behavior behind it for run streaming, durable waits, and workflow declaration execution.
2. Prefer Rust-native types and trait bounds over TS-shaped object bags when the observable behavior is the same, especially for contexts, run refs, and workflow declarations.
3. Land the remaining behavior in this order: durable condition semantics, richer workflow declaration helpers, listener-style run streaming, then the last feature-client gaps.
