# Hatchet Rust SDK — Remaining Work After Initial Parity Pass

## Purpose

This document supersedes the original findings plan in [docs/post_impl_findings/1.md](/Users/christophercaldwell/Code/projects/rust/hatchet_rust_sdk/docs/post_impl_findings/1.md) by focusing only on what is still left to do.

The codebase now has:

- corrected `WorkflowHandle::run` vs `run_no_wait` semantics
- a real `WorkflowRunRef<O>` type with `output`, `cancel`, `replay`, and `stream`
- `RunOpts` reshaped around explicit parent/child linkage
- initial `TaskConfig`, `WorkflowDeclaration`, `ContextExt`, `DurableContextExt`, and `Condition` types
- expanded error taxonomy
- worker handle pause/label methods

Those changes are real, compile, and are covered by tests. The remaining work is mostly about replacing placeholder in-memory behavior with correct runtime semantics and filling in the parts of the TypeScript surface that still only exist as skeletons.

## Remaining Findings

## 1. `TaskConfig` Exists, But Is Not Enforced

`TaskConfig` and related types now exist in [task.rs](/Users/christophercaldwell/Code/projects/rust/hatchet_rust_sdk/crates/hatchet-sdk/src/task.rs), and handles can carry config in [client.rs](/Users/christophercaldwell/Code/projects/rust/hatchet_rust_sdk/crates/hatchet-sdk/src/client.rs). But the runtime does not actually use most of it.

Still missing:

- `execution_timeout` and `schedule_timeout` are not enforced by `WorkerRuntime`
- `retries` and `backoff` do not drive retry behavior
- `rate_limits` are only data, not runtime limits
- `desired_worker_labels` are not used for dispatch decisions
- `concurrency` is not enforced
- `input_schema` is stored but ignored

Required follow-up:

- thread `TaskConfig` into worker registration and dispatch
- enforce timeouts and retry strategy in [worker.rs](/Users/christophercaldwell/Code/projects/rust/hatchet_rust_sdk/crates/hatchet-sdk/src/worker.rs)
- validate input before handler execution
- add runtime tests that prove config changes behavior, not just struct shape

## 2. `WorkflowDeclaration` Is Stored, Not Executed

`WorkflowDeclaration<I, O>` now exists in [workflow.rs](/Users/christophercaldwell/Code/projects/rust/hatchet_rust_sdk/crates/hatchet-sdk/src/workflow.rs), and `Client::register_workflow` serializes it into the in-memory workflows client.

What is still missing:

- no DAG execution engine for declared steps
- no support for `sticky` semantics
- no translation from declaration to worker registrations
- no parent/step dependency scheduler
- no success/failure graph semantics

Right now this is metadata storage, not workflow execution.

Required follow-up:

- define how declared workflows map to runnable in-memory executions
- decide whether a declaration produces a synthetic workflow handler or registration bundle
- add end-to-end tests where `.step_after(...)` actually controls execution order

## 3. `Context` Surface Is Broader, But Several Methods Are Local Stubs

`Context` in [context.rs](/Users/christophercaldwell/Code/projects/rust/hatchet_rust_sdk/crates/hatchet-sdk/src/context.rs) now exposes much more of the TypeScript-style metadata surface.

However:

- `refresh_timeout` is a no-op
- `release_slot` is a no-op
- `put_stream` only appends to an in-memory vector inside the context object
- `log` only records locally inside the context object
- `worker_labels()` returns a cloned snapshot, not a shared runtime view
- parent output/filter payload/trigger data exist only when manually injected into the context constructor helpers

Required follow-up:

- connect logs and streams to the feature clients and/or run records
- decide whether timeout refresh and slot release are meaningful in the in-memory runtime, then implement them
- make trigger data and parent output come from actual execution state rather than test-only setup

## 4. `ContextExt` / `DurableContextExt` Semantics Still Diverge From the Plan

The extension traits are present, but the behavior is still simplified:

- child execution helpers mostly reuse top-level workflow submission
- durable child spawning does not have distinct durable semantics
- child index stability and replay semantics are not guaranteed
- bulk child execution does not model partial failure or exception-return behavior

Required follow-up:

- separate regular child runs from durable child spawns at the runtime layer
- define deterministic child indexing across retries/replays
- add bulk child execution semantics that match the intended TS contract

## 5. `Condition` / `DurableContext` Are Skeletons, Not Durable Runtime Semantics

The type surface in [durable.rs](/Users/christophercaldwell/Code/projects/rust/hatchet_rust_sdk/crates/hatchet-sdk/src/durable.rs) is broader now, but the implementation is still local and optimistic.

Current limitations:

- `supports_eviction()` is hard-coded to `false`
- `wait_for()` is sequential, not a real composed condition waiter
- `Condition::Event` ignores `expression`, `scope`, and `readable_data_key`
- `lookback_window` is only used as a timeout fallback
- `memo()` is an in-memory map without replay/history semantics
- `now()` is memoized per context instance, not per durable history/replay
- durable waiting is based on local timers and broadcast channels, not persisted engine-backed callbacks

Required follow-up:

- decide the minimum durable contract for the in-memory runtime
- implement real condition composition for `or(...)`
- honor event condition fields beyond just `event_key`
- make memoization and time semantics stable across retries/replays
- add tests covering replay determinism and event matching behavior

## 6. Worker Pause/Labels API Exists, But Runtime Routing Is Still Missing

`WorkerHandle` now exposes `pause`, `unpause`, `is_paused`, `upsert_labels`, and `labels` in [worker.rs](/Users/christophercaldwell/Code/projects/rust/hatchet_rust_sdk/crates/hatchet-sdk/src/worker.rs).

What is still missing:

- paused state does not block dispatch
- worker labels are not used by workflow/task routing
- `desired_worker_labels` in `RunOpts` and `TaskConfig` do not influence scheduling
- there is no SIGINT handling path

Required follow-up:

- enforce pause state inside the dispatch loop
- implement label matching during run routing
- connect `desired_worker_labels` to worker selection
- add shutdown-on-SIGINT support for the examples/runtime

## 7. Feature Clients Are Still Mostly In-Memory Facades

The clients compile and basic CRUD-style tests pass, but several parts of Phase 8 are still absent or placeholder-level:

- `RunsClient::subscribe_to_stream()` returns an empty `Vec`
- `branch_durable_task()` just aliases `replay()`
- `restore_task()` only resets queued status
- there is no typed stream event model backing run streaming
- CEL debug is explicitly a local placeholder in [clients.rs](/Users/christophercaldwell/Code/projects/rust/hatchet_rust_sdk/crates/hatchet-sdk/src/clients.rs)
- crons/schedules/events are data stores, not actual trigger mechanisms

Required follow-up:

- define a real `StreamEvent` model and emit it from worker execution
- implement streaming in `WorkflowRunRef::stream()`
- either narrow or fully implement durable admin operations like branch/restore
- decide whether cron/schedule clients in the in-memory runtime should actively trigger workflows

## 8. Input Validation Is Still Missing

The original Phase 10 called for schema-derived validation. The current code only stores `input_schema` in `TaskConfig`.

Still missing:

- no `schemars` integration
- no schema derivation helper
- no validation pass before handler invocation
- no `InputValidation(Vec<String>)` production path in the worker

Required follow-up:

- add schema derivation and validation dependencies
- validate task/workflow input before execution
- return `Error::InputValidation(...)` when validation fails
- extend proc macros to attach schema automatically where appropriate

## 9. Proc Macro Support Improved, But Signature Rewriting Is Still Narrow

The proc-macro tests now cover `impl Context` in one case, but Phase 11 is not fully complete.

Still missing:

- no robust rewrite strategy for all supported `impl Context` / `impl DurableContext` forms
- no broad coverage for generic bounds, lifetimes, or alternate handler signatures
- macros still mostly validate shape rather than normalize signatures comprehensively

Required follow-up:

- explicitly support both concrete context types and `impl Context` / `impl DurableContext`
- harden `function_signature_types` and codegen for generic handlers
- add compile-style tests for all accepted signature forms

## 10. In-Memory Transport and Worker Are Still Not Fully Connected as a Scheduler

Phase 1 fixed result delivery, but the in-memory transport is still not a true routing layer.

Still missing:

- no transport inbox that pushes submitted workflow runs into workers automatically
- examples still manually call worker task runners for most execution
- `Client::workflow(...).run(...)` records a run and awaits transport resolution, but there is no general scheduler bridging workflow submissions to registered tasks/workflows

This is the biggest structural remaining gap if the goal is a realistic in-process SDK.

Required follow-up:

- design how workflow names map to registered tasks/declarations
- connect `InMemoryTransport` submissions to one or more active workers
- eliminate manual “submit run, then separately call worker task” patterns from examples

## Recommended Next Order

If the goal is to keep making real progress rather than adding more type shells, the highest-value remaining order is:

1. Input validation and `TaskConfig` enforcement
2. Worker pause/label routing and runtime dispatch decisions
3. Transport-to-worker scheduling so `workflow.run()` actually drives execution
4. Real run streaming and richer feature-client behavior
5. Durable condition semantics and replay stability
6. Proc-macro signature hardening
7. Full workflow declaration execution semantics

This document can be retired once the following are true:

- task/workflow config changes runtime behavior, not just stored metadata
- `workflow.run()` can execute end-to-end in-memory without manual worker invocation
- streaming, validation, and worker routing work with actual runtime semantics
- durable waits/memo/time behavior are deterministic enough to test meaningfully
- macros support the intended handler signature forms robustly
