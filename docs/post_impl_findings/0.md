# Post-Implementation Findings: Hatchet Rust SDK

## Context

This document records findings from a code review of the LLM-generated Hatchet Rust SDK (crates `hatchet-core`, `hatchet-sdk`, `hatchet-macros`) compared against both the stated goals in `docs/llm_plan/claude/0.md` and the existing unofficial SDK at `sources/hatchet-rust-sdk-main/`.

The review was done before the user's own read-through of the code, to flag issues worth addressing before any further work. The SDK is currently in its in-memory / API-iteration phase — transport parity is explicitly deferred.

---

## Summary Verdict

The generated SDK delivers the API-first, in-memory-backed shape that the plan specified. Abstractions are sound and in many areas (durable context, child runs, proc macros, feature-client breadth) it **goes further than the unofficial SDK**. However, two foundational gaps undermine the value of the typed API: **workflows have no way to return their output** and **`run_no_wait` has no distinct semantics from `run`**. Additionally, handler signatures and the `Context` trait design will force breaking changes when real transport is wired in.

**Ready for next phase?** Not yet. Fix the output-retrieval and `run_no_wait` issues first; revisit the `Context` trait shape before real transport. Everything else is incremental polish.

---

## The Good

### 1. Architecture matches the plan
Three crates as specified: `hatchet-core` (shared types), `hatchet-sdk` (client/worker/contexts), `hatchet-macros` (proc macros). Separation is clean, imports minimal, no circular dependencies.

### 2. Strong type parameterization
`WorkflowHandle<T, I, O>` (`crates/hatchet-sdk/src/client.rs:155-162`), `TaskHandle<I, O>` (`crates/hatchet-sdk/src/client.rs:264-269`), `DurableTaskHandle<I, O>` (`crates/hatchet-sdk/src/client.rs:278-283`) all use `PhantomData<fn(I)>` / `PhantomData<fn() -> O>` — correct variance for input/output positions. This is idiomatic zero-cost Rust.

### 3. Context / DurableContext trait hierarchy
`DurableContext: Context` in `crates/hatchet-sdk/src/durable.rs:22-51`. Matches the TypeScript / Go SDK semantic split. `InMemoryContext` and `InMemoryDurableContext` are concrete implementations — the trait design leaves room for a future real-transport context.

### 4. Rich child-run ergonomics
`crates/hatchet-sdk/src/context.rs:80-192` — `run_child`, `run_child_no_wait`, `bulk_run_children`, `bulk_run_children_no_wait` with typed generics.
`crates/hatchet-sdk/src/durable.rs:92-121` — durable `spawn_child`, `spawn_children`.
All inject parent/child linkage metadata via `child_run_opts` (`context.rs:194-207`) with an atomic `child_index` counter.

This is materially better than the unofficial SDK, which requires users to manually `futures::join_all(workflow.run(...))` to fan out.

### 5. Complete durable primitives
`crates/hatchet-sdk/src/durable.rs:184-252` — `invocation_count`, `now`, `sleep_for`, `sleep_until`, `wait_for_event`, `spawn_child_json`, `spawn_children_json`.
Event fan-out implemented via `tokio::sync::broadcast` (`durable.rs:57, 209-223`) — handles `Lagged` and `Closed` explicitly, returns `Ok(None)` on timeout. Clean design for the in-memory phase.

### 6. Worker runtime with correct concurrency model
`crates/hatchet-sdk/src/worker.rs:201-202` — separate `non_durable_semaphore` and `durable_semaphore`. Default slots: 100 non-durable, 1000 durable (`worker.rs:93-100`). Matches the dual-worker pattern from the plan (`docs/llm_plan/claude/0.md` Phase 3).

Type-erased registry via `ErasedTaskFn<T>` / `ErasedDurableTaskFn<T>` (`worker.rs:20-26`) with `TypedTaskHandler` / `TypedDurableTaskHandler` (`worker.rs:28-78`) — textbook Rust for heterogeneous async closures.

Runtime loop uses `tokio::mpsc` + `JoinSet` + `oneshot` reply channels (`worker.rs:193-213, 410-502`). Graceful shutdown via `WorkItem::Shutdown`.

### 7. Proc macros do signature validation
`crates/hatchet-macros/src/lib.rs:172-209` — validates: must be `async`, must have exactly two arguments, must return `Result<T, _>` or `Result<T>`. Extracts input type and result-ok type. Generates `{fn_name}_task_handle` / `{fn_name}_durable_task_handle` factories plus a const `{FN_NAME}_NAME`.

`#[workflow(name = "...")]` wraps a module and generates a `register_all<T>(...)` function (`lib.rs:74-90`) that wires every `#[task]` / `#[durable_task]` in the module into a `WorkerBuilder`. Ergonomics match the plan.

### 8. Feature-client coverage
`crates/hatchet-sdk/src/client.rs:20-53` registers all 12 feature clients: `runs`, `workflows`, `schedules`, `crons`, `workers`, `metrics`, `rate_limits`, `events`, `logs`, `filters`, `webhooks`, `cel`. Shared `Arc<RwLock<FeatureState>>` for in-memory record keeping. Unofficial SDK only exposes 3 (runs, crons, schedules), so this is a parity improvement.

### 9. Error handling
`thiserror`-derived `Error` enum, `Result<T>` alias used throughout. All public fallible methods return `Result<T>`. Consistent.

### 10. Transport abstraction is clean
`Transport` trait (referenced via `crate::transport::Transport` from `worker.rs`, `client.rs`, `context.rs`) is the right seam. `InMemoryTransport` satisfies it. Swapping in a real gRPC transport will not require touching this layer's call sites.

## The Bad

### 1. CRITICAL — No workflow output retrieval exists
**Files:** `crates/hatchet-core/src/run.rs:36-50`, `crates/hatchet-sdk/src/client.rs:195-212`.

`WorkflowRunRef<O>` holds only `run_id: WorkflowRunId` and `output: PhantomData<fn() -> O>`. There is no `.await`, no `.output()`, no `.wait_for_completion()`, no typed fetch via `client.runs()`. `client.runs().get_status()` returns a status enum, not the typed output.

Consequence: the `O` type parameter is **cosmetic throughout the entire API**. Every typed workflow/task handle produces a typed reference that can never produce a typed value. This is the single largest gap in the SDK.

### 2. CRITICAL — `run` and `run_no_wait` are semantically identical
**File:** `crates/hatchet-sdk/src/client.rs:220-222`:
```rust
pub async fn run_no_wait(&self, input: I, opts: RunOpts) -> Result<WorkflowRunRef<O>> {
    self.run(input, opts).await
}
```
Same pattern in `context.rs:239-246` (`run_child_no_wait_json` just calls `run_child_json`) and `context.rs:259-267` (bulk variant). Both paths return immediately with a `WorkflowRunRef` since nothing ever blocks on completion.

Consequence: the API claims two execution modes but delivers one. Users reading the type signatures are misled. This is connected to issue #1 — `run` can't actually block until output because there's no output retrieval mechanism.

### 3. HIGH — Handler signatures couple to `InMemoryContext<T>`
**File:** `crates/hatchet-sdk/src/worker.rs:39, 65`:
```rust
F: Fn(I, InMemoryContext<T>) -> Fut + Send + Sync + 'static,
F: Fn(I, InMemoryDurableContext<T>) -> Fut + Send + Sync + 'static,
```
All user task handlers must accept the concrete `InMemoryContext<T>` / `InMemoryDurableContext<T>`. This leaks the in-memory implementation type into every user-written task.

Consequence: when a real transport is added, every user-written handler signature will break. This violates the Phase 4 plan goal of "semantic parity while evolving transport independently."

### 4. HIGH — `Context` trait only exposes JSON methods
**File:** `crates/hatchet-sdk/src/context.rs:21-55`. The `Context` trait has:
- `run_child_json`, `run_child_no_wait_json`
- `bulk_run_children_json`, `bulk_run_children_no_wait_json`

The typed versions — `run_child<I, O>`, `bulk_run_children<I, O>` — are **inherent methods** on `InMemoryContext` (`context.rs:80-192`), not trait methods. Same story for `DurableContext` (`durable.rs`): typed methods (`spawn_child`, `spawn_children`) are inherent to `InMemoryDurableContext`, not on the trait.

Consequence: even if handler signatures are changed to `impl Context`, the typed ergonomic API vanishes — users would be forced to hand-call `serde_json::to_value()` and work with `Value`. The trait shape must change before handler-signature decoupling is viable.

### 5. HIGH — Parent/child linkage stored as metadata strings
**File:** `crates/hatchet-sdk/src/context.rs:194-207`. `child_run_opts` injects `parent_workflow_run_id`, `parent_task_run_id`, `child_index` into `opts.metadata` as `Value::String` / `Value::Number` entries.

Consequence: the real Hatchet wire protocol has dedicated protobuf fields for parent linkage (see Go/TS SDKs). This metadata-stuffing approach won't translate to the real transport and will require restructuring `RunOpts` into first-class parent fields.

### 6. MEDIUM — `RunOpts.desired_worker_labels` vs `WorkerBuilder.labels` type mismatch
**Files:** `crates/hatchet-core/src/run.rs:23` (`HashMap<String, String>`) vs `crates/hatchet-sdk/src/worker.rs:84` (`BTreeMap<String, String>`).
The two fields describe the same concept from opposite sides of a match (worker-advertised vs run-requested), but use different map types. Inconsistent.

### 7. MEDIUM — `ContextIds` is a test artifact in public examples
**File:** `crates/hatchet-sdk/src/context.rs:13-19`, used in `examples/src/bin/context_child_runs.rs:80-86` and `examples/src/bin/proc_macros.rs:30-36`.
In production, the runtime would inject these IDs. Having users manually construct `ContextIds { workflow_name: "...", task_name: "...", workflow_run_id: ..., task_run_id: "..." }` in "getting started" examples will confuse readers about which scaffolding is real usage.

### 8. MEDIUM — `WorkerHandle::run_task` / `run_durable_task` expose test-only dispatch
**File:** `crates/hatchet-sdk/src/worker.rs:291-356`. These methods let a caller dispatch tasks directly to the worker by name and typed input. In the real protocol, workers receive tasks from the server, not from their owner.

Consequence: these methods are necessary for the in-memory phase but should be clearly marked test/development-only, or moved behind a feature flag, to prevent users writing code that won't survive the transport switch.

### 9. MEDIUM — `#[workflow]` macro forces `use super::{...}` imports
**File:** `crates/hatchet-macros/src/lib.rs:19-91`. Not a bug in the macro itself — rather, because handlers reference concrete `InMemoryContext<T>` / `InMemoryDurableContext<T>`, user code inside `mod { ... }` must re-import them. This is a downstream symptom of issue #3.

### 10. LOW — Missing `ctx.log()` and streaming
Absent in `crates/hatchet-sdk/src/context.rs`. Both present in the unofficial SDK and first-class in Go/TS. Plan has these as in-scope but deferred.

### 11. LOW — `desired_worker_labels` values are `String`-only
Per plan spec, Hatchet supports richer label values (string/int/bool). `crates/hatchet-core/src/run.rs:23` uses `HashMap<String, String>`.

### 12. LOW — `WorkerHandle::wait` takes `self` but also has a live `shutdown` path
`worker.rs:363-379` — `shutdown(self)` calls `wait(self)`, both consume. Current API is fine but awkward when the same handle is shared across tasks (users will `Arc<Mutex<Option<WorkerHandle>>>` it).

### 13. LOW — No panic isolation around task handlers
Unlike the unofficial SDK (which uses `AssertUnwindSafe` + `catch_unwind`), the generated SDK's `execute_non_durable` / `execute_durable` (`worker.rs:451-501`) will propagate panics through the `JoinSet` and fail the reply channel. A panic in user code takes down the reply with an opaque "channel closed" error.

## Comparison to Unofficial SDK (`sources/hatchet-rust-sdk-main/`)

| Dimension | Generated SDK | Unofficial SDK |
|---|---|---|
| Typed I/O generics | yes | yes |
| Builder pattern | yes (owned fluent) | yes (`derive_builder`) |
| Child runs | first-class | manual `futures::join_all` |
| Durable context | full primitives | absent |
| Proc macros | yes | absent |
| Feature clients | 12 | 3 |
| DAG / parent tasks | no model | `.add_parent()` + `ctx.parent_output()` |
| Output retrieval | **missing** | polling via `get_run()` |
| Real gRPC/REST transport | in-memory only | full wire |
| Streaming / logs | no | yes |
| Handler signature | concrete `InMemoryContext<T>` | opaque `Context` struct |
| JSON-schema input validation | no | via `schemars` |
| Panic safety | no | `catch_unwind` |

The generated SDK is ahead on durable context, child-run ergonomics, macros, and feature-client breadth. The unofficial SDK is ahead on transport, output retrieval, DAG structure, and production hardening. Neither is yet complete; they are complementary blueprints.

## Examples Quality

- `examples/src/bin/declare_and_run.rs` — Good demonstration of `run`, `run_no_wait`, `run_many`, cancel, replay, metrics. Note: the `run_no_wait` distinction is illusory (issue #2).
- `examples/src/bin/context_child_runs.rs` — Demonstrates `bulk_run_children` well. Leaks `ContextIds` construction and `WorkerHandle::run_task` as if they were first-class APIs (issues #7, #8).
- `examples/src/bin/proc_macros.rs` — Clean ergonomically but requires `use super::{DurableContext, InMemoryContext, InMemoryDurableContext, durable_task, task}` inside the macro module (issue #9).
- `examples/src/bin/durable_context.rs` — Reads as a unit test, not a usage demo: manually constructs `InMemoryDurableContext`, spawns a separate `tokio::task` to call `emit_event`. A real-usage demo should show a task handler that calls `ctx.wait_for_event()` with events arriving from the runtime.

## Fix Plan

Ordered by severity / dependency. Later phases depend on earlier ones.

### Phase A — Complete the typed API (critical)

**A1. Add output retrieval to `WorkflowRunRef<O>`.**
- File: `crates/hatchet-core/src/run.rs`
- Change `WorkflowRunRef<O>` to carry a resolver back to an output source rather than `PhantomData`. Options:
  - Add `output_rx: Option<oneshot::Receiver<Value>>` for in-memory.
  - Or keep `run_id` and have an `async fn output(self, transport: &T) -> Result<O>` that calls a new transport method.
- Add `pub async fn output(self) -> Result<O> where O: DeserializeOwned`.
- Consider `impl<O> IntoFuture for WorkflowRunRef<O>` so `.await` works directly.
- In-memory backing: extend `Transport` trait (in `crates/hatchet-sdk/src/transport.rs`) with something like `async fn await_result(&self, run_id: &WorkflowRunId) -> Result<Value>` — the in-memory transport fulfills it from `FeatureState`.

**A2. Make `run_no_wait` genuinely fire-and-forget.**
- File: `crates/hatchet-sdk/src/client.rs:220-222`.
- `run_no_wait` should return `Result<WorkflowRunId>` (or a minimal `WorkflowRunRef` that cannot be `.output()`'d).
- `run` should await completion via the new output-retrieval machinery from A1.
- Apply same change to `context.rs` `run_child` / `run_child_no_wait` pair and `bulk_run_children` / `bulk_run_children_no_wait` pair.

**A3. Verify `WorkerHandle::run_task` / `run_durable_task` end-to-end typing.**
- File: `crates/hatchet-sdk/src/worker.rs:291-356`. Already typed; should automatically benefit from A1.

### Phase B — Decouple handler signatures from `InMemoryContext` (high)

**B1. Move the typed child-run API onto the `Context` trait.**
- File: `crates/hatchet-sdk/src/context.rs:21-55`.
- Preferred shape: add generic default methods (`run_child<I, O>`, `run_child_no_wait<I, O>`, `bulk_run_children<I, O>`, `bulk_run_children_no_wait<I, O>`) that delegate to the JSON trait methods. Generic trait methods aren't `dyn`-safe — if `dyn Context` is ever needed, put the typed API on an extension trait `ContextExt` with a blanket `impl<T: Context + ?Sized> ContextExt for T`.
- Mirror for `DurableContext` in `crates/hatchet-sdk/src/durable.rs:22-51`: move `spawn_child<I, O>`, `spawn_children<I, O>` to trait defaults or a `DurableContextExt`.
- Remove the now-duplicated inherent methods from `InMemoryContext` / `InMemoryDurableContext` (`context.rs:80-192`, `durable.rs:92-121`).

**B2. Change handler bounds from concrete to trait.**
- File: `crates/hatchet-sdk/src/worker.rs:34-78, 122-161`.
- `TypedTaskHandler<T, I, O, F>` should constrain `F` as `Fn(I, Ctx) -> Fut` where `Ctx: Context + Send + 'static`. Because the runtime still constructs `InMemoryContext<T>`, the concrete type is supplied at call time — only the user's closure sees the trait.
- `register_task` / `register_durable_task` accept closures whose second argument is `impl Context` / `impl DurableContext`.

**B3. Update proc macros to generate trait-based handler signatures.**
- File: `crates/hatchet-macros/src/lib.rs:172-209` and `lib.rs:52-67`.
- Either (a) require users to write `impl Context` / `impl DurableContext` in their `#[task]` signatures, and have the macro accept that, or (b) have the macro rewrite whatever context type the user wrote into `impl Context` / `impl DurableContext` before generating registration code.
- Update `register_all` expansion (`lib.rs:74-90`) against the new trait-bound `register_task` / `register_durable_task`.

**B4. Update examples to use traits.**
- `examples/src/bin/proc_macros.rs:13-26` — change `_ctx: InMemoryContext<T>` / `ctx: InMemoryDurableContext<T>` to `_ctx: impl Context` / `ctx: impl DurableContext`.
- `examples/src/bin/context_child_runs.rs:35` — change `ctx: InMemoryContext<_>` to `ctx: impl Context`.
- `examples/src/bin/worker_runtime.rs` (if present) — same change.

### Phase C — Restructure parent/child linkage (high)

**C1. Add first-class parent fields to `RunOpts`.**
- File: `crates/hatchet-core/src/run.rs:17-24`.
- Add:
  ```rust
  pub parent_workflow_run_id: Option<WorkflowRunId>,
  pub parent_task_run_id: Option<String>,
  pub child_index: Option<u64>,
  ```

**C2. Update `child_run_opts` to populate the structured fields.**
- File: `crates/hatchet-sdk/src/context.rs:194-207`.
- Replace metadata stuffing with direct assignment of the new `RunOpts` fields.

**C3. Update example inspection logic.**
- File: `examples/src/bin/context_child_runs.rs:91-97` — switch from `opts.metadata.contains_key("parent_workflow_run_id")` to `opts.parent_workflow_run_id.is_some()` and analogous for `parent_task_run_id`.

### Phase D — Map-type consistency and scaffolding clarity (medium)

**D1. Unify label map types.**
- Decide on one of `BTreeMap<String, String>` (deterministic ordering, good default for labels) or `HashMap<String, String>` (marginally faster, insertion order not guaranteed).
- Update `crates/hatchet-core/src/run.rs:23` (`desired_worker_labels`) and `crates/hatchet-sdk/src/worker.rs:84, 116` (`WorkerBuilder.labels` / `WorkerRuntime._labels`) to match.

**D2. Mark test-only APIs explicitly.**
- Files: `crates/hatchet-sdk/src/worker.rs:237-356`, `crates/hatchet-sdk/src/context.rs:13-19, 64-72`, `crates/hatchet-sdk/src/durable.rs:60-69`.
- Add doc-comment headers on `WorkerHandle::run_task_json`, `run_durable_task_json`, `run_task`, `run_durable_task`, `ContextIds`, `InMemoryContext::new`, `InMemoryDurableContext::new`, `InMemoryDurableContext::emit_event`: "Test-only. Real workers receive tasks from the Hatchet runtime; this helper exists for unit tests and example demos against the in-memory transport."

**D3. Hide in-memory scaffolding in example code.**
- `examples/src/bin/context_child_runs.rs:80-86` and `examples/src/bin/proc_macros.rs:29-36`: move `ContextIds` construction into a local helper (e.g., `fn test_ids(workflow: &str, task: &str) -> ContextIds`) and add a top-of-file comment making it clear that the helper exists only for the in-memory demo and would not be written by a production user.

### Phase E — Runtime robustness (low)

**E1. Add panic isolation in the worker runtime.**
- File: `crates/hatchet-sdk/src/worker.rs:451-501`.
- Wrap `handler.call(input, ctx).await` in `std::panic::AssertUnwindSafe(...).catch_unwind()`. On panic, convert to `Error::Worker(format!("task '{task_name}' panicked"))` and send it through the reply channel instead of letting the channel drop.

**E2. Add `ctx.log()` and streaming primitives.**
- Files: `crates/hatchet-sdk/src/context.rs`, `crates/hatchet-sdk/src/worker.rs`, `crates/hatchet-sdk/src/clients.rs`.
- Add `async fn log(&self, message: &str)` to the `Context` trait with a default implementation that pushes into `FeatureState.logs` via the context's transport / client reference. Matches plan scope and unofficial SDK surface.

**E3. Richer label value types.**
- File: `crates/hatchet-core/src/run.rs:23`.
- Introduce `enum LabelValue { String(String), Int(i64), Bool(bool) }` and change the map to `HashMap<String, LabelValue>` (or `BTreeMap`, per D1). Align with Hatchet engine's real label model. Low priority if examples/tests don't need it yet.

### Phase F — Examples and docs (low)

**F1. Rewrite `examples/src/bin/durable_context.rs` as a realistic usage demo.**
- Show a workflow that calls `ctx.wait_for_event()` from inside a handler, with events produced by a separate actor (e.g., a test harness or another task) via `EventsClient::push`. Stop hand-constructing `InMemoryDurableContext` at the top level.

**F2. Add a top-of-README section** that explicitly calls out:
- Current transport is in-memory and test-oriented.
- Which APIs will change when real transport lands (handler signatures, parent-linkage fields).
- How to migrate when they do.

## Estimated Effort

- Phase A (critical): 1–2 days. Most work is designing the output-retrieval channel on `Transport`.
- Phase B (high): 2–3 days. Trait restructuring plus macro updates. Touches every handler-registration site.
- Phase C (high): half a day. Mechanical field migration.
- Phase D (medium): half a day.
- Phase E (low): 1 day for E1 + E2 combined.
- Phase F (low): half a day.

Total: roughly 5–7 working days to get the SDK into a state where real transport integration (Phase 2 of `docs/llm_plan/claude/0.md`) can begin without forcing breaking changes to user code.
