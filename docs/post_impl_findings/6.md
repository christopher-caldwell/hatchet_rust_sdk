## Findings From This Pass

### 1. Workflow declarations now carry declaration-level conditions

Before this pass, `WorkflowStep` only had `task_name`, `config`, and `parents`. Conditions existed in the durable model but were not part of the workflow declaration API.

Closed gap:

- `WorkflowStep` now has `wait_for: Vec<Conditions>`, `cancel_if: Vec<Conditions>`, and `skip_if: Vec<Conditions>`.
- `WorkflowDeclaration` now has `step_with(...)` and `step_after_with(...)` builder methods that accept a `StepConditions` builder.
- `StepConditions` is a fluent builder that mirrors the TS `waitFor`, `cancelIf`, and `skipIf` fields on `CreateWorkflowTaskOpts`.
- The existing `step(...)` and `step_after(...)` methods remain unchanged and initialize empty condition vecs.

Why this matters:

- This is the first time Rust workflow declarations can express TS-style condition-aware step composition.
- The condition model created in `5.md` is now connected to the workflow declaration API surface.

### 2. Parent conditions now exist in Rust with full parity to the TS `ParentCondition` class

Before this pass, Rust had no parent-condition concept at all.

Closed gap:

- New `Condition::Parent(ParentCondition)` variant.
- New `Condition::parent(task_name)` constructor returning `ParentConditionBuilder`.
- `ParentConditionBuilder` supports `.expression(...)`, `.readable_data_key(...)`, `.action(...)`, `.or_group_id(...)`, and `.build()`.
- Default `readable_data_key` is `"parent-{task_name}"`, matching the TS default of `"parent-${parent.name}"`.
- Parent conditions participate in OR group assignment and action defaulting.

Why this matters:

- Parent conditions are the third condition type in the TS hierarchy (alongside sleep and user-event).
- Without them, skip-if-parent and cancel-if-parent patterns are impossible in declarations.

### 3. Parent conditions render into protocol-shaped `ParentOverrideMatchCondition`

Closed gap:

- `RenderedConditions` now has a `parent_override_conditions: Vec<ParentOverrideMatchCondition>` field.
- `ParentOverrideMatchCondition` has `base: BaseMatchCondition` and `parent_readable_id: String`.
- `conditions_to_rendered(...)` routes parent conditions to this new output bucket.
- Expression and readable-key propagation works identically to event and sleep conditions.

Why this matters:

- This matches the TS `conditionsToPb(...)` contract which produces `parentOverrideConditions: ParentOverrideMatchCondition[]`.

### 4. All condition types are now serializable

Before this pass, `Condition`, `Conditions`, and their inner types did not derive `Serialize`/`Deserialize`.

Closed gap:

- All condition types now derive `Serialize`, `Deserialize`, and `PartialEq`.
- `Duration` fields use a `serde_duration_millis` helper (millisecond representation).
- `SystemTime` fields use a `serde_system_time_millis` helper (epoch milliseconds).
- `WorkflowStep` condition fields are serialized with `skip_serializing_if = "Vec::is_empty"` to avoid noise for steps without conditions.
- Serde round-trip is tested explicitly.

Why this matters:

- Conditions must survive serialization to participate in workflow declaration transport/registration payloads.
- This was a blocker for `WorkflowStep` using `Vec<Conditions>` since `WorkflowStep` already derived `Serialize`/`Deserialize`.

### 5. Durable runtime correctly handles parent conditions with explicit error semantics

Parent conditions require engine-backed resolution. The in-memory durable context now:

- Returns `Error::Durable("parent conditions require engine-backed resolution")` from `wait_for_condition` for parent conditions.
- Returns `None` (never immediately resolvable) from `resolve_ready_pending` for parent conditions.
- Handles the `Parent` variant in all `match` exhaustiveness positions alongside event and sleep.

## Updated Bottom Line

The Rust SDK condition model is now feature-complete at the model and declaration level:

What is now true:

- Rust conditions have first-class metadata (from `5.md`)
- OR grouping is explicit (from `5.md`)
- Protocol-shaped rendering exists (from `5.md`)
- **NEW**: Parent conditions are fully implemented
- **NEW**: Workflow declarations can express `waitFor`, `cancelIf`, `skipIf`
- **NEW**: All condition types are serializable for transport
- **NEW**: The condition model is connected to the workflow declaration API

What is still true:

- Transport/protocol code does not yet consume the rendered structures
- The durable runtime is still in-memory, not listener/engine backed
- `WorkflowRunRef` and run observation are still weaker than TS

The remaining gap is no longer "the condition model is not integrated into declarations."

The remaining gap is:

- The condition model exists and is integrated into declarations
- But transport/protocol transformation and engine-backed execution still do not exist
